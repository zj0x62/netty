# SCTP / UDT / RXTX 传输

## 概述

除了 TCP/UDP 和 Unix Domain Socket 之外，Netty 还支持三种特殊的传输协议：SCTP（流控制传输协议）、UDT（基于 UDP 的可靠数据传输协议）和 RXTX（串口通信）。这些传输适用于特定的网络场景，使用范围远不如 TCP/UDP 广泛。

## 一、三种 IO 模型对比

在深入各传输之前，先对比 Netty 支持的三种核心 I/O 模型：

### 就绪通知 vs 完成通知

```
+------------------+-------------------+-------------------+-------------------+
|                  | epoll (Linux)     | kqueue (BSD)      | io_uring (Linux)  |
+------------------+-------------------+-------------------+-------------------+
| 通知模型         | 就绪通知          | 就绪通知          | 完成通知          |
|                  | "fd 可以读了"     | "过滤器满足了"    | "I/O 帮你做完了"  |
+------------------+-------------------+-------------------+-------------------+
| 核心 API         | epoll_create()    | kqueue()          | io_uring_setup()  |
|                  | epoll_ctl()       | kevent()          | io_uring_enter()  |
|                  | epoll_wait()      |                   | SQ/CQ 共享内存    |
+------------------+-------------------+-------------------+-------------------+
| 注册方式         | epoll_ctl(ADD)    | changeList.add()  | 写入 SQ           |
|                  | epoll_ctl(MOD)    |                   | (SQE)             |
|                  | epoll_ctl(DEL)    |                   |                   |
+------------------+-------------------+-------------------+-------------------+
| 事件标识         | fd (int)          | ident+filter      | UserData 打包     |
|                  |                   | (long+short)      | (id+op+data)      |
+------------------+-------------------+-------------------+-------------------+
| 唤醒机制         | eventfd           | EVFILT_USER       | eventfd           |
+------------------+-------------------+-------------------+-------------------+
| 定时机制         | timerfd           | kevent timeout    | IORING_OP_TIMEOUT |
+------------------+-------------------+-------------------+-------------------+
| 零拷贝支持       | 无（需 sendfile） | 无                | IORING_OP_SEND_ZC |
+------------------+-------------------+-------------------+-------------------+
| 批量操作         | epoll_wait 一次   | kevent 一次       | SQ 批量提交       |
|                  | 返回多个事件      | 返回多个事件      | CQ 批量收割       |
+------------------+-------------------+-------------------+-------------------+
| 系统调用次数     | 每次读写 1 次     | 每次读写 1 次     | 可以 0 次         |
| (单次 I/O)       | + epoll_wait 1 次 | + kevent 1 次     | (SQPOLL 模式)     |
+------------------+-------------------+-------------------+-------------------+
| 异步程度         | 事件等待异步      | 事件等待异步      | 全部操作异步      |
|                  | I/O 同步执行      | I/O 同步执行      | (connect/close等) |
+------------------+-------------------+-------------------+-------------------+
| 平台             | Linux             | macOS/FreeBSD     | Linux 5.1+        |
+------------------+-------------------+-------------------+-------------------+
| Netty 引入版本   | 4.0               | 4.1               | 4.2 (实验性)      |
+------------------+-------------------+-------------------+-------------------+
| 稳定性           | 生产就绪          | 生产就绪          | 持续迭代中        |
+------------------+-------------------+-------------------+-------------------+
```

### 事件处理模型对比

```
epoll 模型（同步 I/O）:
  epoll_wait() ──> 返回 fd 列表
      │
      ├──> fd1 EPOLLIN  ──> read(fd1)  ──> 处理数据
      ├──> fd2 EPOLLOUT ──> write(fd2) ──> 发送数据
      └──> fd3 EPOLLIN  ──> read(fd3)  ──> 处理数据

io_uring 模型（异步 I/O）:
  提交 SQE: RECV(fd1), SEND(fd2), RECV(fd3), ACCEPT(fd4)
      │
      └──> io_uring_enter() ──> 内核异步执行
              │
              ├──> CQE: RECV(fd1) 完成, res=N bytes
              ├──> CQE: SEND(fd2) 完成, res=M bytes
              ├──> CQE: RECV(fd3) 完成, res=K bytes
              └──> CQE: ACCEPT(fd4) 完成, res=new_fd
```

## 二、SCTP 传输

### 概述

SCTP（Stream Control Transmission Protocol，流控制传输协议）是一种面向消息的传输层协议，结合了 TCP 的可靠性和 UDP 的消息边界特性。Netty 通过 JDK 的 `com.sun.nio.sctp` API 实现 SCTP 支持。

**模块**: `transport-sctp`

**核心特性**:
- 多流（Multi-streaming）: 一个连接中包含多个独立的流
- 多宿（Multi-homing）: 一个端点可以绑定多个 IP 地址
- 消息边界: 原生支持消息边界，无需像 TCP 那样处理粘包/拆包
- 有序/无序交付: 支持按序和无序的消息传递

**平台要求**:
- Linux: 需要安装 `lksctp-tools` 并加载 SCTP 内核模块
- 需要 JDK 7+

### 核心类

```
SctpChannel (接口)
    │
    ├── NioSctpChannel        // NIO 实现（常用）
    └── OioSctpChannel        // OIO 实现（兼容）

SctpServerChannel (接口)
    │
    ├── NioSctpServerChannel  // NIO 服务端实现
    └── OioSctpServerChannel  // OIO 服务端实现

SctpMessage                   // SCTP 消息封装
SctpNotificationHandler       // SCTP 通知处理器
```

### NioSctpChannel 实现要点

`NioSctpChannel` 继承自 `AbstractNioMessageChannel`，使用 JDK 的 `SctpChannel`:

```java
public class NioSctpChannel extends AbstractNioMessageChannel
        implements io.netty.channel.sctp.SctpChannel {
    private final SctpChannelConfig config;
    private final NotificationHandler<?> notificationHandler;
    private ByteBuffer inputCopy;
    private ByteBuffer outputCopy;
}
```

**关键操作**:
- **读取**: 通过 `javaChannel().read()` 读取 `ByteBuffer` 和 `MessageInfo`，封装为 `SctpMessage`
- **写入**: 通过 `javaChannel().send()` 发送 `ByteBuffer`，附带流号和 payload 协议 ID
- **多流支持**: 每个 `SctpMessage` 携带 `streamNumber`，不同流的消息独立交付

### SCTP 编解码器

Netty 提供了 SCTP 专用的编解码器:

| 编解码器 | 功能 |
|---------|------|
| `SctpMessageCompletionHandler` | 将分片的 SCTP 消息重组为完整消息 |
| `SctpInboundByteStreamHandler` | 从指定流中读取字节数据 |
| `SctpOutboundByteStreamHandler` | 向指定流中写入字节数据 |
| `SctpMessageToMessageDecoder` | SCTP 消息到消息的解码 |

## 三、UDT 传输

### 概述

UDT（UDP-based Data Transfer）是一种基于 UDP 的高性能数据传输协议，专为高带宽长距离网络（如跨大洲的科学数据传输）设计。Netty 通过第三方 Java UDT 库实现 UDT 支持。

**模块**: `transport-udt`

**状态**: 已废弃（`@Deprecated`），不再维护，将在未来版本移除。

**核心特性**:
- 基于 UDP 的可靠传输
- 支持字节流和消息两种模式
- 支持 Rendezvous（对等连接）模式
- 专为高带宽长距离网络优化

### 核心类

```
UdtChannel (接口)
    │
    ├── NioUdtByteConnectorChannel     // 字节流连接器
    ├── NioUdtByteAcceptorChannel      // 字节流接受器
    ├── NioUdtByteRendezvousChannel    // 字节流对等连接
    ├── NioUdtMessageConnectorChannel  // 消息连接器
    ├── NioUdtMessageAcceptorChannel   // 消息接受器
    └── NioUdtMessageRendezvousChannel // 消息对等连接

NioUdtProvider  // UDT 传输提供者
```

### UDT 模式

| 模式 | 说明 |
|------|------|
| Byte Connector | 字节流客户端模式 |
| Byte Acceptor | 字节流服务端模式 |
| Byte Rendezvous | 字节流对等连接模式 |
| Message Connector | 消息客户端模式 |
| Message Acceptor | 消息服务端模式 |
| Message Rendezvous | 消息对等连接模式 |

### Rendezvous 模式

UDT 的 Rendezvous 模式是其独特特性，允许两个端点同时发起连接（类似 TCP 的 Simultaneous Open）:

```
端点 A                                    端点 B
  |                                         |
  +---- 绑定地址 A ----+                    +---- 绑定地址 B ----
  |                                         |
  +---- connect(B) ---->                    <---- connect(A) ----+
  |                                         |
  +<---- 连接建立 ----->+<---- 连接建立 ---->+
```

## 四、RXTX 传输

### 概述

RXTX 传输提供了串口（Serial Port）通信支持，允许 Netty 通过串口收发数据。使用 gnu.io (RXTX) Java 库访问操作系统串口。

**模块**: `transport-rxtx`

**状态**: 已废弃（`@Deprecated`），将在下一个主版本移除。

**核心特性**:
- 串口数据收发
- 支持配置波特率、数据位、停止位、校验位
- 支持 DTR/RTS 控制信号
- 基于 OIO（Old I/O）实现

### 核心类

```java
public class RxtxChannel extends OioByteStreamChannel {
    private final RxtxChannelConfig config;
    private RxtxDeviceAddress deviceAddress;
    private SerialPort serialPort;
}
```

**配置选项**:

| 选项 | 说明 | 类型 |
|------|------|------|
| `BAUD_RATE` | 波特率 | int |
| `DATA_BITS` | 数据位 (5/6/7/8) | int |
| `STOP_BITS` | 停止位 (1/1.5/2) | StopBits |
| `PARITY_BIT` | 校验位 (None/Odd/Even) | Parity |
| `DTR` | Data Terminal Ready | boolean |
| `RTS` | Request To Send | boolean |
| `READ_TIMEOUT` | 读超时 (ms) | int |
| `WAIT_TIME` | 等待时间 (ms) | int |

**地址模型**:

```java
// 串口地址以设备路径标识
new RxtxDeviceAddress("/dev/ttyUSB0")   // Linux
new RxtxDeviceAddress("COM3")           // Windows
```

## 五、总结

### 各传输适用场景

| 传输 | 适用场景 | 状态 |
|------|---------|------|
| **epoll** | Linux 生产环境，高并发 TCP/UDP | 推荐 |
| **kqueue** | macOS/BSD 生产环境 | 推荐 |
| **io_uring** | Linux 5.1+，追求极致性能 | 实验性 |
| **SCTP** | 电信信令、多宿网络 | 可用 |
| **UDT** | 科学计算、大数据传输 | 已废弃 |
| **RXTX** | 串口设备通信 | 已废弃 |

### 如何选择传输

```
需要网络通信？
    │
    ├── TCP/UDP
    │       │
    │       ├── Linux ──> epoll (稳定) 或 io_uring (极致性能)
    │       ├── macOS ──> kqueue
    │       └── 其他  ──> JDK NIO
    │
    ├── 需要多流/多宿？
    │       └── SCTP
    │
    ├── 高带宽长距离 UDP？
    │       └── UDT (已废弃，考虑替代方案)
    │
    └── 串口通信？
            └── RXTX (已废弃，考虑替代方案)
```

### 学习要点

1. **SCTP 的多流特性**: SCTP 的多流（Multi-streaming）允许在一个连接中创建多个独立的流，每个流的消息独立交付，避免了 TCP 中队头阻塞（Head-of-Line Blocking）的问题。

2. **UDT 的设计理念**: UDT 专为高带宽长距离网络设计，使用 UDP 作为底层传输，通过自定义的拥塞控制和可靠传输机制来优化大数据量传输。

3. **RXTX 的局限性**: RXTX 基于 OIO 实现，性能有限且库维护不活跃。串口通信场景可以考虑 jSerialComm 等替代方案。

4. **io_uring 是未来方向**: 从 Netty 4.2 的发展趋势来看，io_uring 代表了 Linux 异步 I/O 的未来。虽然当前仍标记为实验性，但其零拷贝、批量提交、全异步等特性使其在高并发场景下具有显著优势。

5. **三模型的本质区别**: epoll/kqueue 是"通知你去操作"（就绪通知），io_uring 是"我帮你操作完了"（完成通知）。这个根本区别决定了 io_uring 在高并发场景下可以显著减少系统调用次数。
