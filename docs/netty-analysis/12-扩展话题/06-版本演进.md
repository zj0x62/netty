# Netty 版本演进

## 概述

Netty 自 2004 年诞生以来，经历了多次重大架构演进。本文梳理 Netty 3.x → 4.x → 4.2 → 5.x 的设计变迁，理解框架发展的脉络。

---

## 一、版本时间线

```
2004 ──── 2008 ──── 2011 ──── 2013 ──── 2016 ──── 2019 ──── 2024 ──── 2025
  │         │         │         │         │         │         │         │
  ▼         ▼         ▼         ▼         ▼         ▼         ▼         ▼
Netty 1   Netty 2   Netty 3   Netty 4   Netty 4.1 Netty 4.2 Netty 4.2 未来
(Mina子项目) (独立)  (稳定)   (重构)   (长期支持) (改进)  (当前)
```

## 二、Netty 3.x → 4.x：架构重构

### 2.1 核心变化

| 维度 | Netty 3.x | Netty 4.x |
|------|-----------|-----------|
| **Buffer** | `ChannelBuffer` | `ByteBuf` |
| **线程模型** | I/O 线程 + 业务线程池 | EventLoop 单线程模型 |
| **内存管理** | 堆内存为主 | 直接内存 + 内存池 |
| **对象池化** | 无 | Recycler |
| **零拷贝** | 有限支持 | CompositeByteBuf、slice、duplicate |

### 2.2 Buffer 重构

**Netty 3.x**：
```java
// ChannelBuffer — 绑定到 Channel
public interface ChannelBuffer {
    int readerIndex();
    int writerIndex();
    byte readByte();
    void writeByte(int value);
}
```

**Netty 4.x**：
```java
// ByteBuf — 独立于 Channel
public abstract class ByteBuf {
    int readerIndex();
    int writerIndex();
    byte readByte();
    ByteBuf writeByte(int value);
    ByteBuf slice();
    ByteBuf duplicate();
    CompositeByteBuf compositeBuffer();
}
```

**改进**：
- ByteBuf 不再绑定到 Channel，可独立使用
- 支持池化分配（PooledByteBufAllocator）
- 支持零拷贝操作（slice、duplicate、composite）
- 引入引用计数（ReferenceCounted）管理生命周期

### 2.3 线程模型重构

**Netty 3.x**：
```
┌─────────────────────────────────────────────────┐
│           NioServerSocketPipelineSink            │
│  ┌───────────────────────────────────────────┐  │
│  │  I/O Worker Thread 0 (Selector 轮询)      │  │
│  │  I/O Worker Thread 1                      │  │
│  │  ...                                      │  │
│  └───────────────────────────────────────────┘  │
│                      ↓ 事件                      │
│  ┌───────────────────────────────────────────┐  │
│  │  Business Thread Pool (业务处理)           │  │
│  │  ┌─────────┬─────────┬─────────┐         │  │
│  │  │ Thread0 │ Thread1 │ Thread2 │         │  │
│  │  └─────────┴─────────┴─────────┘         │  │
│  └───────────────────────────────────────────┘  │
└─────────────────────────────────────────────────┘
```

**Netty 4.x**：
```
┌─────────────────────────────────────────────────┐
│              EventLoopGroup                      │
│  ┌───────────────────────────────────────────┐  │
│  │  EventLoop 0 (I/O + 业务，单线程串行)      │  │
│  │  ├── Channel 0                            │  │
│  │  ├── Channel 1                            │  │
│  │  └── Channel 2                            │  │
│  ├───────────────────────────────────────────┤  │
│  │  EventLoop 1                              │  │
│  │  ├── Channel 3                            │  │
│  │  └── Channel 4                            │  │
│  └───────────────────────────────────────────┘  │
└─────────────────────────────────────────────────┘
```

**改进**：
- 消除 I/O 线程和业务线程的切换
- 无锁串行化，避免同步开销
- 简化线程模型，降低复杂度

### 2.4 API 变化

| 3.x API | 4.x API | 说明 |
|---------|---------|------|
| `ChannelHandler` | `ChannelInboundHandler` / `ChannelOutboundHandler` | 分离入站和出站 |
| `ChannelBuffer` | `ByteBuf` | 独立于 Channel |
| `Channels` 工具类 | `ChannelHandlerContext` | 上下文驱动 |
| `ExecutionHandler` | EventLoop 内置 | 业务线程池可选 |
| `ChannelFuture` | `ChannelFuture` + `GenericFutureListener` | 增强异步编程 |

## 三、Netty 4.x → 4.1：长期支持版

### 3.1 主要改进

1. **HTTP/2 支持**：`netty-codec-http2` 模块
2. **DNS 解析**：`netty-resolver-dns` 模块
3. **原生传输增强**：epoll、kernet、kqueue 优化
4. **内存分配器优化**：Arena 分配策略改进
5. **ResourceLeakDetector**：资源泄漏检测

### 3.2 关键特性

```java
// HTTP/2 支持
Http2ConnectionDecoder decoder = new DefaultHttp2ConnectionDecoder(...);
Http2ConnectionEncoder encoder = new DefaultHttp2ConnectionEncoder(...);

// DNS 解析
DnsNameResolver resolver = new DnsNameResolverBuilder(eventLoop)
    .channelType(NioDatagramChannel.class)
    .build();

// 资源泄漏检测
ResourceLeakDetector.setLevel(ResourceLeakDetector.Level.PARANOID);
```

## 四、Netty 4.1 → 4.2：架构改进

### 4.1 IoHandler 抽象（核心变化）

**4.1**：各传输层独立实现 EventLoop
```java
// 4.1：NioEventLoop 直接处理 Selector
public final class NioEventLoop extends SingleThreadEventLoop {
    private Selector selector;
    // 与 Selector 紧耦合
}

// 4.1：EpollEventLoop 直接处理 epoll
public final class EpollEventLoop extends SingleThreadEventLoop {
    private final FileDescriptor epollFd;
    // 与 epoll 紧耦合
}
```

**4.2**：统一的 IoHandler 接口
```java
// 4.2：统一的 IoHandler 抽象
public interface IoHandler {
    int run(IoHandlerContext context);
    IoRegistration register(IoHandle handle) throws Exception;
    void wakeup();
}

// 实现类
NioIoHandler      // Java NIO
EpollIoHandler    // Linux epoll
IoUringIoHandler  // Linux io_uring
```

**改进**：
- 传输层实现与 EventLoop 解耦
- 新增传输层只需实现 IoHandler 接口
- `MultiThreadIoEventLoopGroup` 统一管理

### 4.2 io_uring 支持

```java
// 4.2 新增：io_uring 传输层
IoUringIoHandlerConfig config = new IoUringIoHandlerConfig();
if (IoUring.isRegisterBufferRingSupported()) {
    config.setBufferRingConfig(
        IoUringBufferRingConfig.builder()
            .bufferGroupId((short) 0)
            .bufferRingSize((short) 16)
            .allocator(new IoUringFixedBufferRingAllocator(1024))
            .build()
    );
}
EventLoopGroup group = new MultiThreadIoEventLoopGroup(
    IoUringIoHandler.newFactory(config));
```

### 4.3 AdaptiveByteBufAllocator

```java
// 4.2 新增：自适应内存分配器
// 基于反代际假说（Anti-generational Hypothesis）
// 认为大多数对象生命周期短，少数对象生命周期长
ByteBufAllocator allocator = new AdaptiveByteBufAllocator();
```

### 4.4 AutoScalingEventExecutorChooserFactory

```java
// 4.2 新增：基于利用率的自动伸缩选择器
// 根据 EventLoop 负载动态分配 Channel
EventExecutorChooserFactory factory = new AutoScalingEventExecutorChooserFactory();
EventLoopGroup group = new MultiThreadIoEventLoopGroup(
    0, null, factory, NioIoHandler.newFactory());
```

### 4.5 虚拟线程支持

```java
// 4.2 改进：虚拟线程兼容
// EventLoop 可以使用虚拟线程（Java 21+）
Executor executor = Executors.newVirtualThreadPerTaskExecutor();
EventLoopGroup group = new MultiThreadIoEventLoopGroup(
    executor, NioIoHandler.newFactory());
```

## 五、Netty 5.x：曾经的方向（已废弃）

### 5.1 尝试的特性

Netty 5.x 分支曾尝试以下改进，但最终被废弃：

1. **AttributeKey 改进**：更灵活的属性系统
2. **ByteBuf 接口简化**：减少抽象方法
3. **Handler 生命周期重构**：简化状态管理

### 5.2 废弃原因

- **API 变化过大**：与 4.x 不兼容，迁移成本高
- **收益不明显**：改进不足以说服用户升级
- **社区反馈**：用户更希望 4.x 持续改进

### 5.3 教训

- **向后兼容性**：大规模 API 变更需要谨慎
- **渐进式改进**：小步快跑优于大步跳跃
- **社区共识**：重大变更需要充分讨论

## 六、设计哲学演进

### 6.1 从"大而全"到"小而精"

```
Netty 3.x: 尝试提供完整的网络应用框架
    ↓
Netty 4.x: 专注于网络编程基础设施
    ↓
Netty 4.2: 模块化 + 可插拔的传输层
```

### 6.2 性能优化的优先级

| 版本 | 优化重点 |
|------|----------|
| 3.x | 功能完整性 |
| 4.0 | 内存池化、零拷贝 |
| 4.1 | HTTP/2、DNS、原生传输 |
| 4.2 | io_uring、自适应分配、虚拟线程 |

### 6.3 API 设计原则

1. **Zero-Copy 优先**：尽量避免数据复制
2. **无锁设计**：EventLoop 单线程模型
3. **可扩展性**：Handler/Filter 可插拔
4. **向后兼容**：新版本尽量兼容旧 API

## 七、迁移指南

### 7.1 从 3.x 迁移到 4.x

```java
// 3.x
ChannelHandler handler = new SimpleChannelHandler() {
    @Override
    public void messageReceived(ChannelHandlerContext ctx, MessageEvent e) {
        ChannelBuffer buf = (ChannelBuffer) e.getMessage();
    }
};

// 4.x
ChannelInboundHandlerAdapter handler = new ChannelInboundHandlerAdapter() {
    @Override
    public void channelRead(ChannelHandlerContext ctx, Object msg) {
        ByteBuf buf = (ByteBuf) msg;
    }
};
```

### 7.2 从 4.1 迁移到 4.2

```java
// 4.1
NioEventLoopGroup group = new NioEventLoopGroup();  // @Deprecated

// 4.2
EventLoopGroup group = new MultiThreadIoEventLoopGroup(NioIoHandler.newFactory());

// 4.1
EpollEventLoopGroup group = new EpollEventLoopGroup();  // @Deprecated

// 4.2
EventLoopGroup group = new MultiThreadIoEventLoopGroup(EpollIoHandler.newFactory());
```

## 学习要点

1. **4.x 是分水岭**：从 ChannelBuffer 到 ByteBuf，从双线程到单线程 EventLoop
2. **4.2 是新起点**：IoHandler 抽象为传输层扩展奠定基础
3. **5.x 的教训**：向后兼容性比激进创新更重要
4. **性能优化持续**：内存池、零拷贝、无锁设计贯穿始终
5. **模块化设计**：从紧耦合到可插拔，框架越来越灵活
