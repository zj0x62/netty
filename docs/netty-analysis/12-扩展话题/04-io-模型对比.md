# NIO vs Epoll vs io_uring：三种 IO 模型对比

## 概述

Netty 4.2 提供了三种 IO 模型的实现，分别基于 Java NIO、Linux epoll 和 Linux io_uring。本文对比这三种实现的架构差异、性能特征和适用场景。

---

## 一、架构对比

### 统一的 IoHandler 抽象

Netty 4.2 引入 `IoHandler` 接口，统一了不同 IO 模型的抽象：

```java
// IoHandler.java — 4.2 统一接口
public interface IoHandler {
    void initialize();
    int run(IoHandlerContext context);
    void prepareToDestroy();
    void destroy();
    IoRegistration register(IoHandle handle) throws Exception;
    void wakeup();
    boolean isCompatible(Class<? extends IoHandle> handleType);
}
```

### 三种实现对比

```
┌─────────────────────────────────────────────────────────────────────┐
│                    MultiThreadIoEventLoopGroup                      │
│                    (统一的 EventLoop 管理)                           │
├─────────────────────────────────────────────────────────────────────┤
│   IoHandlerFactory                                                  │
│   ┌─────────────────┬─────────────────┬─────────────────┐          │
│   │  NioIoHandler   │ EpollIoHandler  │ IoUringIoHandler│          │
│   │   (Java NIO)    │  (Linux epoll)  │ (Linux io_uring)│          │
│   └────────┬────────┴────────┬────────┴────────┬────────┘          │
│            │                 │                 │                    │
│   ┌────────┴────────┬────────┴────────┬────────┴────────┐          │

│   └─────────────────┴────────────────┴─────────────────┘          │
└─────────────────────────────────────────────────────────────────────┘
```

## 二、详细对比

### 2.1 Java NIO（NioIoHandler）

#### 核心机制

```java
// NioIoHandler.java
public final class NioIoHandler implements IoHandler {
    private final Selector selector;  // JDK Selector

    @Override
    public int run(IoHandlerContext context) {
        // 1. select() 阻塞等待事件
        int selectedKeys = selector.select(timeout);
        // 2. 遍历 SelectionKey 处理事件
        processSelectedKeys(selector.selectedKeys());
        // 3. 运行任务队列
        runTasks();
        return selectedKeys;
    }
}
```

#### 事件模型

```
┌──────────────────────────────────────────────┐
│              Selector (epoll/kqueue)          │
│  ┌───────────────────────────────────────┐   │
│  │         SelectionKey Set              │   │
│  │  ┌─────────┬─────────┬─────────┐     │   │
│  │  │ OP_READ │OP_WRITE │OP_ACCEPT│     │   │
│  │  └────┬────┴────┬────┴────┬────┘     │   │
│  └───────┼─────────┼─────────┼──────────┘   │
│          │         │         │               │
│  ┌───────┴─────────┴─────────┴──────────┐   │
│  │        Channel (Socket/Server)        │   │
│  └──────────────────────────────────────┘   │
└──────────────────────────────────────────────┘
```

#### 优势
- 跨平台（Windows/Linux/macOS）
- 无需额外依赖
- JDK 官方支持

#### 劣势
- 系统调用开销（用户态↔内核态切换）
- 事件通知需复制到用户空间
- 每次 select() 需遍历所有注册的 Channel

### 2.2 Linux epoll（EpollIoHandler）

#### 核心机制

```java
// EpollIoHandler.java
public class EpollIoHandler implements IoHandler {
    private FileDescriptor epollFd;   // epoll 文件描述符
    private FileDescriptor eventFd;   // 唤醒用 eventfd
    private FileDescriptor timerFd;   // 定时器用 timerfd
    private final EpollEventArray events;  // 事件数组

    @Override
    public int run(IoHandlerContext context) {
        // 1. epoll_wait() 等待事件
        int ready = epollWait(deadlineNanos);
        // 2. 直接遍历就绪事件（无需遍历所有）
        for (int i = 0; i < ready; i++) {
            handle(events.fd(i), events.events(i));
        }
        // 3. 运行任务队列
        runTasks();
        return ready;
    }
}
```

#### 事件模型

```
┌──────────────────────────────────────────────┐
│              epoll (内核)                     │
│  ┌───────────────────────────────────────┐   │
│  │         红黑树（注册的 fd）            │   │
│  │    fd1 ─→ fd2 ─→ fd3 ─→ ...          │   │
│  └───────────────────┬───────────────────┘   │
│                      │ 事件就绪              │
│  ┌───────────────────┴───────────────────┐   │
│  │         就绪链表（Ready List）          │   │
│  │    fd2 ─→ fd5 ─→ fd8                  │   │
│  └───────────────────┬───────────────────┘   │
└──────────────────────┼───────────────────────┘
                       │ epoll_wait()
┌──────────────────────┴───────────────────────┐
│              EpollIoHandler (用户)            │
│  只处理就绪的 fd，无需遍历所有               │
└──────────────────────────────────────────────┘
```

#### JNI 调用

```c
// netty-transport-native-epoll 中的 JNI 实现
JNIEXPORT jint JNICALL Java_io_netty_channel_epoll_Native_epollWait0(
    JNIEnv* env, jclass clazz, jint efd, jlong address, jint len, jint timeout) {
    struct epoll_event* events = (struct epoll_event*)(intptr_t)address;
    return epoll_wait(efd, events, len, timeout);
}
```

#### 优势
- 就绪通知效率 O(1)（vs NIO 的 O(n)）
- 支持 ET（边缘触发）模式，减少事件通知次数
- 支持 timerfd，避免额外的定时器线程

#### 劣势
- 仅限 Linux
- 需要 JNI 原生库
- 仍有用户态↔内核态切换

### 2.3 Linux io_uring（IoUringIoHandler）

#### 核心机制

```java
// IoUringIoHandler.java
public final class IoUringIoHandler implements IoHandler {
    private final RingBuffer ringBuffer;  // SQ/CQ 环形缓冲区
    private final FileDescriptor eventfd;

    @Override
    public int run(IoHandlerContext context) {
        // 1. 提交 SQE（Submission Queue Entry）
        submitPendingSubmissions();
        // 2. 等待 CQE（Completion Queue Entry）
        int processed = processCompletions();
        // 3. 运行任务队列
        runTasks();
        return processed;
    }
}
```

#### 事件模型

```
┌──────────────────────────────────────────────────────────────────┐
│                        io_uring (内核)                           │
│  ┌────────────────────────────────────────────────────────────┐ │
│  │                    Submission Queue (SQ)                    │ │
│  │  ┌──────┬──────┬──────┬──────┬──────┐                     │ │
│  │  │ SQE0 │ SQE1 │ SQE2 │ SQE3 │ ...  │  ← 提交 IO 请求    │ │
│  │  └──────┴──────┴──────┴──────┴──────┘                     │ │
│  │  head ─────────────────────────────→ tail                  │ │
│  └────────────────────────────────────────────────────────────┘ │
│                              ↓ 内核异步处理                      │
│  ┌────────────────────────────────────────────────────────────┐ │
│  │                   Completion Queue (CQ)                     │ │
│  │  ┌──────┬──────┬──────┬──────┬──────┐                     │ │
│  │  │ CQE0 │ CQE1 │ CQE2 │ CQE3 │ ...  │  ← 获取完成结果    │ │
│  │  └──────┴──────┴──────┴──────┴──────┘                     │ │
│  │  head ─────────────────────────────→ tail                  │ │
│  └────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────┴────────────────────────────────────┐
│                    IoUringIoHandler (用户)                        │
│  通过 mmap 共享内存，无需系统调用即可提交和获取结果              │
└──────────────────────────────────────────────────────────────────┘
```

#### 关键特性

```java
// Buffer Ring 支持（4.2 新增）
IoUringIoHandlerConfig config = new IoUringIoHandlerConfig();
if (IoUring.isRegisterBufferRingSupported()) {
    config.setBufferRingConfig(
        IoUringBufferRingConfig.builder()
            .bufferGroupId((short) 0)
            .bufferRingSize((short) 16)
            .batchSize(16)
            .allocator(new IoUringFixedBufferRingAllocator(1024))
            .build()
    );
}
```

#### 优势
- **零系统调用**：SQ/CQ 通过 mmap 共享，提交和获取无需 syscall
- **真正的异步**：内核后台处理 IO，完成后通知用户
- **批量提交**：一次 `io_uring_enter()` 提交多个请求
- **Buffer Ring**：预注册缓冲区，减少内核↔用户态数据复制

#### 劣势
- 仅限 Linux 5.1+（推荐 5.10+）
- 需要较新的 JNI 原生库
- 调试相对困难

## 三、性能对比

### 延迟对比

| 操作 | NIO | epoll | io_uring |
|------|-----|-------|----------|
| 单次 read() | ~1μs | ~0.8μs | ~0.5μs |
| 单次 write() | ~1μs | ~0.8μs | ~0.5μs |
| 1000 次批量操作 | ~1000μs | ~800μs | ~200μs |

**说明**：数据为典型场景估算，实际性能取决于硬件和负载。

### 吞吐量对比

```
场景：10KB 数据块，单线程 EventLoop

NIO:      ████████████████████████████ 100% (基准)
epoll:    ██████████████████████████████████ 120%
io_uring: ████████████████████████████████████████ 160%
```

### 系统调用次数对比

| 场景 | NIO | epoll | io_uring |
|------|-----|-------|----------|
| 读取 100 个连接 | 100 次 read() + 1 次 select() | 100 次 read() + 1 次 epoll_wait() | 1 次 io_uring_enter() |
| 写入 100 个连接 | 100 次 write() + 1 次 select() | 100 次 write() + 1 次 epoll_wait() | 1 次 io_uring_enter() |

## 四、使用方式

### 统一 API（推荐）

```java
// 4.2 推荐方式：使用统一的 MultiThreadIoEventLoopGroup
IoHandlerFactory factory;

// 根据平台选择
if (IoUring.isAvailable()) {
    factory = IoUringIoHandler.newFactory();
} else if (Epoll.isAvailable()) {
    factory = EpollIoHandler.newFactory();
} else {
    factory = NioIoHandler.newFactory();
}

EventLoopGroup group = new MultiThreadIoEventLoopGroup(factory);
```

### 传统方式（已废弃）

```java
// 已废弃：特定平台的 EventLoopGroup
NioEventLoopGroup nioGroup = new NioEventLoopGroup();       // @Deprecated
EpollEventLoopGroup epollGroup = new EpollEventLoopGroup(); // @Deprecated
```

## 五、适用场景

| 场景 | 推荐 IO 模型 | 原因 |
|------|-------------|------|
| 开发/测试环境 | NIO | 跨平台，无需原生库 |
| 生产环境（Linux） | epoll | 成熟稳定，性能优秀 |
| 高并发低延迟 | io_uring | 批量提交，零拷贝 |
| Windows 环境 | NIO | 唯一支持选项 |
| macOS 环境 | NIO | epoll 不可用 |

## 六、迁移指南

### 从 NIO 迁移到 epoll

```java
// 之前
EventLoopGroup group = new NioEventLoopGroup();
ServerBootstrap b = new ServerBootstrap();
b.group(group).channel(NioServerSocketChannel.class);

// 之后（4.2 推荐）
EventLoopGroup group = new MultiThreadIoEventLoopGroup(EpollIoHandler.newFactory());
ServerBootstrap b = new ServerBootstrap();
b.group(group).channel(EpollServerSocketChannel.class);
```

### 从 epoll 迁移到 io_uring

```java
// 之前
EventLoopGroup group = new MultiThreadIoEventLoopGroup(EpollIoHandler.newFactory());

// 之后
IoUringIoHandlerConfig config = new IoUringIoHandlerConfig();
// 可选：配置 Buffer Ring
EventLoopGroup group = new MultiThreadIoEventLoopGroup(IoUringIoHandler.newFactory(config));
```

## 学习要点

1. **统一抽象**：`IoHandler` 接口屏蔽了底层差异，上层代码无需修改
2. **渐进式升级**：NIO → epoll → io_uring，根据平台和需求选择
3. **io_uring 是未来**：零系统调用 + 真正异步，适合极致性能场景
4. **epoll 仍是主流**：成熟稳定，生产环境首选
5. **NIO 不可或缺**：跨平台兼容性保证
