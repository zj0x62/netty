# Netty 性能调优要点

## 概述

Netty 的高性能并非偶然，而是通过一系列精心设计的优化手段实现的。本文整理 Netty 中的核心性能优化技术，帮助开发者理解框架的性能内核。

---

## 一、内存池化 — PooledByteBufAllocator

### 问题背景

频繁的 `malloc/free` 调用会导致：
- 系统调用开销
- 内存碎片
- GC 压力（堆内存）

### Netty 解决方案

```
┌─────────────────────────────────────────────────────────┐
│                PooledByteBufAllocator                    │
├─────────────────────────────────────────────────────────┤
│  ThreadLocal Cache (FastThreadLocal)                    │
│    └── PoolThreadCache                                  │
│         ├── smallSubPageHeapCaches (<= pageSize)        │
│         ├── normalHeapCaches (> pageSize)               │
│         ├── smallSubPageDirectCaches                    │
│         └── normalDirectCaches                          │
├─────────────────────────────────────────────────────────┤
│  Arena Pool (多个 Arena 减少竞争)                        │
│    ├── HeapArena[0] ... HeapArena[n]                    │
│    └── DirectArena[0] ... DirectArena[n]                │
│         └── ChunkList                                   │
│              ├── qInit (50-100%)                         │
│              ├── q000 (25-75%)                           │
│              ├── q025 (0-50%)                            │
│              ├── q050 (1-25%)                            │
│              ├── q075 (0-5%)                             │
│              └── q100 (0-1%)                             │
└─────────────────────────────────────────────────────────┘
```

### 关键参数

| 参数 | 系统属性 | 默认值 | 说明 |
|------|----------|--------|------|
| Heap Arena 数量 | `io.netty.allocator.numHeapArenas` | CPU核数×2 | 减少堆内存分配竞争 |
| Direct Arena 数量 | `io.netty.allocator.numDirectArenas` | CPU核数×2 | 减少直接内存分配竞争 |
| 页大小 | `io.netty.allocator.pageSize` | 8192 | 内存分配最小单位 |
| 最大阶数 | `io.netty.allocator.maxOrder` | 9 | Chunk = pageSize << maxOrder = 4MB |
| 小缓存大小 | `io.netty.allocator.smallCacheSize` | 256 | ThreadLocal 小对象缓存 |
| 普通缓存大小 | `io.netty.allocator.normalCacheSize` | 64 | ThreadLocal 普通对象缓存 |
| 缓存对齐 | `io.netty.allocator.directMemoryCacheAlignment` | 0 | 直接内存对齐字节数 |

### 分配流程

```java
// 1. 先查 ThreadLocal 缓存（无锁）
PoolThreadCache cache = threadCache.get();
if (cache.allocateSmall(...)) return;

// 2. 缓存未命中，访问 Arena（可能有锁）
if (arena.allocate(...)) return;

// 3. Arena 也没有可用内存，分配新 Chunk
arena.allocateHuge(...);
```

## 二、对象池化 — Recycler

### 设计目标

减少短生命周期对象的 GC 压力，如 `ChannelHandlerContext`、`WriteTask` 等。

### 核心实现

```java
// Recycler.java
public abstract class Recycler<T> {
    // ThreadLocal + 轻量级栈
    private final FastThreadLocal<LocalPool<T>> threadLocal;

    private static final class LocalPool<T> {
        private final int ratio;        // 回收比例控制
        private final int maxCapacity;  // 最大缓存数量
        private final WeakOrderQueue transferQueue;  // 跨线程回收队列
        private DefaultHandle<T> head;  // 栈顶
    }
}
```

### 使用方式

```java
private static final Recycler<ByteBuf> RECYCLER = new Recycler<ByteBuf>() {
    @Override
    protected ByteBuf newObject(Handle<ByteBuf> handle) {
        return new PooledByteBuf(handle, ...);
    }
};

// 获取对象
ByteBuf buf = RECYCLER.get();

// 使用完毕后回收
buf.release();  // 内部调用 handle.recycle(this)
```

### 跨线程回收

```
Thread A (生产者)           Thread B (消费者)
    │                           │
    │  create object            │
    │      │                    │
    │  object.recycle()         │
    │      │                    │
    │  写入 WeakOrderQueue ──────→ 从 transferQueue 获取
    │                           │
```

- `WeakOrderQueue` 使用链表结构，避免锁竞争
- 通过 `WeakReference` 允许 GC 回收不再使用的队列

## 三、零拷贝技术

### CompositeByteBuf

```java
// 将多个 ByteBuf 合并为一个逻辑视图，不复制数据
CompositeByteBuf composite = allocator.compositeBuffer();
composite.addComponents(true, header, body, footer);

// 对外表现为一个连续的 ByteBuf
composite.readByte();  // 从 header 开始读取
```

**原理**：
- 内部维护 `Component[]` 数组，记录每个 ByteBuf 的偏移和长度
- 读写时根据索引定位到对应的底层 ByteBuf
- 不复制底层数据，只记录元信息

### SlicedByteBuf / DuplicatedByteBuf

```java
ByteBuf original = allocator.buffer(1024);

// 切片：共享底层数据，只改变索引
ByteBuf slice = original.slice(100, 200);

// 复制：共享底层数据和索引
ByteBuf duplicate = original.duplicate();
```

### Gathering Write

```java
// 一次系统调用写入多个 ByteBuf
ByteBuffer[] buffers = {buf1.nioBuffer(), buf2.nioBuffer()};
channel.write(buffers);  // 底层调用 GatheringByteChannel.write(ByteBuffer[])
```

**优势**：减少系统调用次数，适合 HTTP 响应头+Body 的场景。

## 四、无锁串行化 — EventLoop 单线程模型

### 核心设计

```
┌──────────────────────────────────────────────┐
│              EventLoopGroup                   │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐      │
│  │EventLoop0│ │EventLoop1│ │EventLoop2│      │
│  │ Thread-0 │ │ Thread-1 │ │ Thread-2 │      │
│  └────┬─────┘ └────┬─────┘ └────┬─────┘      │
│       │            │            │             │
│  ┌────┴────┐  ┌────┴────┐  ┌────┴────┐       │
│  │Channel0 │  │Channel2 │  │Channel4 │       │
│  │Channel1 │  │Channel3 │  │Channel5 │       │
│  └─────────┘  └─────────┘  └─────────┘       │
└──────────────────────────────────────────────┘
```

### 无锁保证

1. **单线程执行**：每个 Channel 的所有 I/O 操作由同一个 EventLoop 线程执行
2. **任务队列串行化**：非 I/O 线程提交的任务进入 MPSC 队列，由 EventLoop 线程串行执行
3. **无需同步**：ChannelPipeline 中的 Handler 访问无需加锁

```java
// SingleThreadEventExecutor.java
private final Queue<Runnable> taskQueue;  // MPSC 队列

// 添加任务（可从任意线程调用）
execute(Runnable task) {
    if (inEventLoop()) {
        // 当前线程就是 EventLoop，直接执行
        addTask(task);
    } else {
        // 外部线程，加入队列并唤醒
        offerTask(task);
        wakeup(inEventLoop);
    }
}
```

## 五、自适应缓冲区大小 — AdaptiveRecvByteBufAllocator

### 设计目标

根据实际数据量动态调整接收缓冲区大小，避免：
- 缓冲区过小：频繁读取，增加系统调用
- 缓冲区过大：内存浪费

### 实现机制

```java
// AdaptiveRecvByteBufAllocator.java
public class AdaptiveRecvByteBufAllocator extends DefaultMaxMessagesRecvByteBufAllocator {
    public static final int DEFAULT_MINIMUM = 64;
    public static final int DEFAULT_INITIAL = 2048;  // 大于常见 MTU 1500
    public static final int DEFAULT_MAXIMUM = 65536;

    // 自适应调整逻辑
    @Override
    public void lastBytesRead(int bytes) {
        if (bytes == attemptedBytesRead()) {
            // 读满了缓冲区，可能有更多数据，增大预测值
            calculator.record(bytes);
        }
        super.lastBytesRead(bytes);
    }
}
```

### 调整算法

```
实际读取 = 缓冲区大小 → 增大下次预测值
实际读取 < 缓冲区大小 × 50% → 减小下次预测值（连续两次）
其他情况 → 保持当前预测值
```

## 六、FastThreadLocal

### 与标准 ThreadLocal 的对比

| 特性 | ThreadLocal | FastThreadLocal |
|------|-------------|-----------------|
| 查找方式 | Hash 表 | 数组索引 |
| 时间复杂度 | O(1) 平均，可能哈希冲突 | O(1) 恒定 |
| 适用线程 | 任意线程 | FastThreadLocalThread |
| 内存占用 | 线性增长 | 按索引分配 |

### 实现原理

```java
// FastThreadLocal.java
public class FastThreadLocal<V> {
    private final int index;  // 全局递增的唯一索引

    public V get() {
        InternalThreadLocalMap threadLocalMap = InternalThreadLocalMap.get();
        Object v = threadLocalMap.indexedVariable(index);  // O(1) 数组访问
        if (v != InternalThreadLocalMap.UNSET) {
            return (V) v;
        }
        return initialize(threadLocalMap);
    }
}

// InternalThreadLocalMap.java
public final class InternalThreadLocalMap {
    private Object[] indexedVariables;  // 数组存储，索引即 ID

    public Object indexedVariable(int index) {
        Object[] lookup = indexedVariables;
        return index < lookup.length ? lookup[index] : UNSET;
    }
}
```

### 使用场景

- `PooledByteBufAllocator` 的 `PoolThreadCache`
- `DefaultChannelPipeline` 的 `nameCaches`
- `Recycler` 的 `LocalPool`

## 七、内存对齐

### 概念

内存对齐确保数据结构的起始地址是某个值（通常是 2 的幂）的倍数。

### Netty 的应用

```java
// 直接内存缓存对齐
int defaultAlignment = SystemPropertyUtil.getInt(
    "io.netty.allocator.directMemoryCacheAlignment", 0);

// 对齐后的内存访问可以利用 CPU 缓存行
// 避免 false sharing（伪共享）
```

### 伪共享问题

```
┌─────────────────────────────────────┐
│           CPU Cache Line (64B)      │
│  ┌───────────┐  ┌───────────┐      │
│  │ Thread A  │  │ Thread B  │      │
│  │ variable  │  │ variable  │      │
│  └───────────┘  └───────────┘      │
└─────────────────────────────────────┘
  修改 A 会导致 B 的缓存失效！
```

**解决方案**：使用 `@Contended` 注解或手动填充缓存行。

## 八、性能调优清单

### 系统参数调优

```properties
# 内存分配器
-Dio.netty.allocator.numHeapArenas=4
-Dio.netty.allocator.numDirectArenas=4
-Dio.netty.allocator.pageSize=8192
-Dio.netty.allocator.maxOrder=9
-Dio.netty.allocator.smallCacheSize=256
-Dio.netty.allocator.normalCacheSize=64
-Dio.netty.allocator.directMemoryCacheAlignment=64

# 对象回收器
-Dio.netty.recycler.maxCapacityPerThread=4096
-Dio.netty.recycler.ratio=8

# 接收缓冲区
-Dio.netty.channel.udp.maxDatagramPayloadSize=65535

# 日志级别（生产环境）
-Dio.netty.leakDetection.level=DISABLED
```

### 代码层面调优

1. **使用直接内存**：减少堆内存 GC
   ```java
   ByteBuf buf = allocator.directBuffer(1024);
   ```

2. **使用 CompositeByteBuf**：避免数据复制
   ```java
   CompositeByteBuf composite = allocator.compositeBuffer();
   ```

3. **使用 Gathering Write**：减少系统调用
   ```java
   channel.write(buf1);
   channel.write(buf2);
   channel.flush();  // 合并写入
   ```

4. **避免在 Handler 中阻塞**：使用异步操作
   ```java
   // 错误示例
   ctx.writeAndFlush(msg).sync();  // 阻塞 EventLoop

   // 正确示例
   ctx.writeAndFlush(msg).addListener(future -> {
       // 异步回调
   });
   ```

5. **合理设置 ByteBuf 大小**：利用自适应分配器
   ```java
   // 使用自适应分配器（4.2 新增）
   ByteBufAllocator allocator = new AdaptiveByteBufAllocator();
   ```

## 学习要点

1. **池化是核心**：无论是内存还是对象，池化都是 Netty 高性能的基础
2. **无锁设计**：EventLoop 单线程模型消除了大部分同步需求
3. **零拷贝**：通过视图和引用共享，避免不必要的数据复制
4. **自适应**：根据实际使用情况动态调整资源分配
5. **缓存友好**：内存对齐和 FastThreadLocal 考虑了 CPU 缓存特性
