# Netty 编解码框架（一）：ByteToMessageDecoder 与 MessageToByteEncoder

## 一、概述

Netty 的编解码框架是整个网络通信的核心骨架。在 TCP 等流式协议中，数据以无边界的字节流形式到达，应用层需要将其转换为有意义的业务消息（解码），同时将业务消息转换为字节流发送（编码）。Netty 通过 `codec-base` 模块提供了一套完整的编解码抽象体系。

本文聚焦于最基础的两个类：

- **ByteToMessageDecoder** -- 将字节流解码为消息对象（入站方向）
- **MessageToByteEncoder** -- 将消息对象编码为字节流（出站方向）

以及它们的组合体 **ByteToMessageCodec** 和辅助类 **CodecOutputList**。

## 三、核心类分析

### 3.1 ByteToMessageDecoder

**类声明与继承关系：**

```java
public abstract class ByteToMessageDecoder extends ChannelInboundHandlerAdapter
```

继承 `ChannelInboundHandlerAdapter`，是入站方向的 Handler。构造函数中调用 `ensureNotSharable()`，标记该 Handler 不可共享（因为内部持有可变状态 `cumulation`）。

#### 3.1.1 核心字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `cumulation` | `ByteBuf` | 累积缓冲区，将多次到达的字节数据合并为一个连续缓冲区 |
| `cumulator` | `Cumulator` | 累积策略，默认为 `MERGE_CUMULATOR` |
| `singleDecode` | `boolean` | 是否每次 channelRead 只解码一条消息，默认 false |
| `decodeState` | `byte` | 解码状态机：`STATE_INIT` / `STATE_CALLING_CHILD_DECODE` / `STATE_HANDLER_REMOVED_PENDING` |
| `numReads` | `int` | 读取次数计数器，达到 `discardAfterReads`（默认16）后触发 discard |
| `inputMessages` | `Queue<Object>` | 重入保护队列，处理递归 channelRead 调用 |
| `firedChannelRead` | `boolean` | 本轮是否已向下游 fire 过 channelRead |
| `first` | `boolean` | 标记 cumulation 是否为首次创建 |

#### 3.1.2 Cumulator 累积策略

`Cumulator` 是一个函数式接口，定义了字节缓冲区的累积策略：

```java
public interface Cumulator {
    ByteBuf cumulate(ByteBufAllocator alloc, ByteBuf cumulation, ByteBuf in);
}
```

Netty 提供了两种内置实现：

**MERGE_CUMULATOR（默认）：**
- 将 `in` 的数据拷贝到 `cumulation` 中
- 策略细节：
  1. 若 `cumulation == in`，直接返回（避免重复 release）
  2. 若 `cumulation` 无数据且 `in` 是连续的，直接用 `in` 替换
  3. 若 `cumulation` 容量不足或被共享（refCnt > 1）或只读，调用 `expandCumulation()` 扩容
  4. 否则将 `in` 的数据写入 `cumulation`

**COMPOSITE_CUMULATOR：**
- 使用 `CompositeByteBuf` 零拷贝组合
- 避免内存拷贝，但 `CompositeByteBuf` 的索引实现更复杂，某些场景可能更慢

`expandCumulation()` 方法的实现：
```java
static ByteBuf expandCumulation(ByteBufAllocator alloc, ByteBuf oldCumulation, ByteBuf in) {
    int oldBytes = oldCumulation.readableBytes();
    int newBytes = in.readableBytes();
    int totalBytes = oldBytes + newBytes;
    ByteBuf newCumulation = alloc.buffer(alloc.calculateNewCapacity(totalBytes, Integer.MAX_VALUE));
    // 将旧数据和新数据拷贝到新缓冲区
    newCumulation.setBytes(0, oldCumulation, oldCumulation.readerIndex(), oldBytes)
        .setBytes(oldBytes, in, in.readerIndex(), newBytes)
        .writerIndex(totalBytes);
    in.readerIndex(in.writerIndex());
    // 释放旧缓冲区
    oldCumulation.release();
    return newCumulation;
}
```

#### 3.1.3 channelRead() -- 核心入口

`channelRead()` 是解码的主入口，实现了完整的状态机逻辑：

```
channelRead(input)
    |
    +-- decodeState == STATE_INIT?
    |       |
    |       +-- YES: 正常解码流程
    |       |     |
    |       |     +-- input 是 ByteBuf?
    |       |     |     |
    |       |     |     +-- YES:
    |       |     |     |   1. first = (cumulation == null)
    |       |     |     |   2. cumulation = cumulator.cumulate(累积)
    |       |     |     |   3. callDecode(ctx, cumulation, out)
    |       |     |     |   4. 处理 cumulation 生命周期
    |       |     |     |   5. fireChannelRead 向下游传递
    |       |     |     |
    |       |     |     +-- NO: 直接 ctx.fireChannelRead(input)
    |       |     |
    |       |     +-- 检查 inputMessages 队列（重入消息）
    |       |
    |       +-- NO: 重入调用
    |             |
    |             +-- 将 input 放入 inputMessages 队列
    |                 (由外层调用统一处理)
```

**重入保护机制：** 当 `decodeState != STATE_INIT` 时（即正在调用子类 `decode()`），新的 `channelRead` 调用不会立即处理，而是将消息放入 `inputMessages` 队列。外层循环通过 `do-while` 消费队列中的消息。

**cumulation 生命周期管理（finally 块）：**
1. 若 `cumulation` 已无数据可读，释放并置 null
2. 若读取次数达到 `discardAfterReads`，调用 `discardSomeReadBytes()` 回收已读字节的内存
3. 将解码结果通过 `fireChannelRead()` 传递给下游

#### 3.1.4 callDecode() -- 解码循环

```java
protected void callDecode(ChannelHandlerContext ctx, ByteBuf in, List<Object> out) {
    while (in.isReadable()) {
        int outSize = out.size();
        if (outSize > 0) {
            fireChannelRead(ctx, out, outSize);  // 先将已有结果传递
            out.clear();
            if (ctx.isRemoved()) break;          // Handler 已移除则停止
        }

        int oldInputLength = in.readableBytes();
        decodeRemovalReentryProtection(ctx, in, out);  // 调用子类 decode()

        if (ctx.isRemoved()) break;

        if (out.isEmpty()) {
            if (oldInputLength == in.readableBytes()) {
                break;    // 没产出消息也没消费字节 -> 数据不足，等待更多数据
            } else {
                continue; // 消费了字节但没产出消息 -> 继续尝试
            }
        }

        if (oldInputLength == in.readableBytes()) {
            throw new DecoderException("decode() did not read anything but decoded a message.");
        }

        if (isSingleDecode()) break;  // 单次解码模式
    }
}
```

**关键设计：**
- 循环调用 `decode()` 直到没有数据可读或没有消息产出
- 每轮先检查是否有已解码消息需要传递（避免延迟）
- 通过比较 `oldInputLength` 和当前 `readableBytes()` 判断是否消费了数据
- `isSingleDecode()` 为 true 时只解码一条消息就退出（用于协议升级等场景）

#### 3.1.5 decodeRemovalReentryProtection() -- 移除重入保护

```java
final void decodeRemovalReentryProtection(ChannelHandlerContext ctx, ByteBuf in, List<Object> out) {
    decodeState = STATE_CALLING_CHILD_DECODE;
    try {
        decode(ctx, in, out);
    } finally {
        if (inputMessages == null || inputMessages.isEmpty()) {
            boolean removePending = decodeState == STATE_HANDLER_REMOVED_PENDING;
            decodeState = STATE_INIT;
            if (removePending) {
                fireChannelRead(ctx, out, out.size());
                out.clear();
                handlerRemoved(ctx);
            }
        }
    }
}
```

**状态机设计：**
- `STATE_INIT`：初始状态，可以接受新的 channelRead
- `STATE_CALLING_CHILD_DECODE`：正在调用子类 decode()，此时的 channelRead 进入重入队列
- `STATE_HANDLER_REMOVED_PENDING`：在 decode() 过程中 Handler 被移除，需要延迟处理

#### 3.1.6 handlerRemoved() -- Handler 移除

```java
public final void handlerRemoved(ChannelHandlerContext ctx) {
    if (decodeState == STATE_CALLING_CHILD_DECODE) {
        decodeState = STATE_HANDLER_REMOVED_PENDING;  // 延迟处理
        return;
    }
    ByteBuf buf = cumulation;
    if (buf != null) {
        cumulation = null;
        numReads = 0;
        int readable = buf.readableBytes();
        if (readable > 0) {
            ctx.fireChannelRead(buf);      // 将剩余数据传递给下游
            ctx.fireChannelReadComplete();
        } else {
            buf.release();
        }
    }
    handlerRemoved0(ctx);
}
```

**要点：** 移除时不能丢弃未解码的数据，需要将 `cumulation` 中剩余的可读字节传递给下游 Handler。

#### 3.1.7 channelReadComplete() 与 discardSomeReadBytes()

```java
public void channelReadComplete(ChannelHandlerContext ctx) {
    numReads = 0;
    discardSomeReadBytes();
    // 非自动读取模式下，如果没有产出消息，需要主动触发下一次读取
    if (selfFiredChannelRead && !firedChannelRead && !ctx.channel().config().isAutoRead()) {
        ctx.read();
    }
    firedChannelRead = false;
    selfFiredChannelRead = false;
    ctx.fireChannelReadComplete();
}

protected final void discardSomeReadBytes() {
    if (cumulation != null && !first && cumulation.refCnt() == 1) {
        cumulation.discardSomeReadBytes();
    }
}
```

**discard 机制：**
- 仅在 `refCnt == 1` 时才 discard（防止在 `slice().retain()` 等场景下破坏外部持有的视图）
- 不在 `first`（cumulation 刚创建）时 discard
- `discardSomeReadBytes()` 会移动 `readerIndex` 前面的已读字节，释放内存

#### 3.1.8 channelInputClosed() 与 decodeLast()

当连接关闭（`channelInactive`）或输入关闭（`ChannelInputShutdownEvent`）时：

```java
void channelInputClosed(ChannelHandlerContext ctx, List<Object> out) {
    if (cumulation != null) {
        callDecode(ctx, cumulation, out);  // 先尝试正常解码
        if (!ctx.isRemoved()) {
            ByteBuf buffer = cumulation == null ? Unpooled.EMPTY_BUFFER : cumulation;
            decodeLast(ctx, buffer, out);  // 最后一次解码机会
        }
    } else {
        decodeLast(ctx, Unpooled.EMPTY_BUFFER, out);
    }
}
```

`decodeLast()` 默认实现：
```java
protected void decodeLast(ChannelHandlerContext ctx, ByteBuf in, List<Object> out) {
    if (in.isReadable()) {
        decodeRemovalReentryProtection(ctx, in, out);
    }
}
```

子类可以覆盖 `decodeLast()` 进行特殊清理（例如处理半关闭状态下的残留数据）。

### 3.2 MessageToByteEncoder

**类声明：**

```java
public abstract class MessageToByteEncoder<I> extends ChannelOutboundHandlerAdapter
```

出站方向的 Handler，将消息对象编码为 `ByteBuf`。

#### 3.2.1 核心字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `matcher` | `TypeParameterMatcher` | 泛型类型匹配器，用于判断消息是否可被此编码器处理 |
| `preferDirect` | `boolean` | 是否优先分配 Direct Buffer，默认 true |

#### 3.2.2 write() -- 编码入口

```java
public void write(ChannelHandlerContext ctx, Object msg, ChannelPromise promise) {
    ByteBuf buf = null;
    try {
        if (acceptOutboundMessage(msg)) {
            I cast = (I) msg;
            buf = allocateBuffer(ctx, cast, preferDirect);  // 分配输出缓冲区
            try {
                encode(ctx, cast, buf);                      // 子类编码
            } finally {
                ReferenceCountUtil.release(cast);            // 释放输入消息
            }

            if (buf.isReadable()) {
                ctx.write(buf, promise);                     // 传递编码结果
            } else {
                buf.release();
                ctx.write(Unpooled.EMPTY_BUFFER, promise);   // 空消息
            }
            buf = null;
        } else {
            ctx.write(msg, promise);  // 类型不匹配，直接传递
        }
    } catch (EncoderException e) {
        throw e;
    } catch (Throwable e) {
        throw new EncoderException(e);
    } finally {
        if (buf != null) buf.release();  // 异常时释放缓冲区
    }
}
```

**关键设计：**
1. `TypeParameterMatcher` 通过反射获取泛型参数 `I` 的类型，实现自动类型匹配
2. `allocateBuffer()` 默认分配 Direct Buffer（`preferDirect=true`），子类可覆盖以优化容量
3. 编码完成后自动释放输入消息（`ReferenceCountUtil.release(cast)`）
4. 编码结果为空时发送 `Unpooled.EMPTY_BUFFER`，保证 promise 被通知

#### 3.2.3 allocateBuffer() -- 缓冲区分配

```java
protected ByteBuf allocateBuffer(ChannelHandlerContext ctx, I msg, boolean preferDirect) {
    if (preferDirect) {
        return ctx.alloc().ioBuffer();    // Direct Buffer
    } else {
        return ctx.alloc().heapBuffer();  // Heap Buffer
    }
}
```

子类可以覆盖此方法，根据消息大小预估合适的初始容量，减少扩容次数。

### 3.3 CodecOutputList

`CodecOutputList` 是编解码框架的内部优化类，用于替代 `ArrayList<Object>` 作为解码输出容器。

#### 3.3.1 设计动机

解码过程中需要频繁创建临时 List 来收集解码结果。使用标准 `ArrayList` 会产生大量 GC 压力。`CodecOutputList` 通过以下优化减少开销：

1. **线程本地缓存池**：每个线程缓存 16 个 `CodecOutputList` 实例
2. **环形缓冲区复用**：`CodecOutputLists` 内部使用环形数组管理缓存
3. **延迟清空**：`clear()` 只重置 `size`，不清理数组元素
4. **批量回收**：`recycle()` 时才真正清理数组并归还到缓存池

#### 3.3.2 核心方法

```java
// 获取实例（优先从缓存池获取）
static CodecOutputList newInstance() {
    return CODEC_OUTPUT_LISTS_POOL.get().getOrCreate();
}

// 添加元素（带自动扩容）
public boolean add(Object element) {
    try {
        insert(size, element);
    } catch (IndexOutOfBoundsException ignore) {
        expandArray();    // 扩容为原来的 2 倍
        insert(size, element);
    }
    ++size;
    return true;
}

// 快速清空（不清理数组）
public void clear() {
    maxSeenSize = Math.max(maxSeenSize, size);
    size = 0;
}

// 回收（清理数组并归还缓存池）
void recycle() {
    int len = Math.max(maxSeenSize, size);
    for (int i = 0; i < len; i++) {
        array[i] = null;  // 帮助 GC
    }
    size = 0;
    maxSeenSize = 0;
    insertSinceRecycled = false;
    recycler.recycle(this);
}
```

#### 3.3.3 insertSinceRecycled 标志

```java
boolean insertSinceRecycled() {
    return insertSinceRecycled;
}
```

该标志用于 `ByteToMessageDecoder.channelRead()` 中判断本轮是否产出了消息：
```java
firedChannelRead |= out.insertSinceRecycled();
```

如果没有产出任何消息且非自动读取模式，需要主动调用 `ctx.read()` 触发下一次读取，避免死锁。

### 3.4 ByteToMessageCodec

**类声明：**

```java
public abstract class ByteToMessageCodec<I> extends ChannelDuplexHandler
```

组合了 `ByteToMessageDecoder` 和 `MessageToByteEncoder`，同时处理入站解码和出站编码。

#### 3.4.1 内部组合结构

```java
// 内部解码器 -- 匿名类，委托给外部类的 decode()
private final ByteToMessageDecoder decoder = new ByteToMessageDecoder() {
    public void decode(ChannelHandlerContext ctx, ByteBuf in, List<Object> out) {
        ByteToMessageCodec.this.decode(ctx, in, out);
    }
    protected void decodeLast(ChannelHandlerContext ctx, ByteBuf in, List<Object> out) {
        ByteToMessageCodec.this.decodeLast(ctx, in, out);
    }
};

// 内部编码器 -- 私有类，委托给外部类的 encode()
private final class Encoder extends MessageToByteEncoder<I> {
    protected void encode(ChannelHandlerContext ctx, I msg, ByteBuf out) {
        ByteToMessageCodec.this.encode(ctx, msg, out);
    }
}
```

#### 3.4.2 事件委托

```java
public void channelRead(ChannelHandlerContext ctx, Object msg) {
    decoder.channelRead(ctx, msg);           // 入站 -> 解码器
}

public void write(ChannelHandlerContext ctx, Object msg, ChannelPromise promise) {
    encoder.write(ctx, msg, promise);         // 出站 -> 编码器
}

public void handlerAdded(ChannelHandlerContext ctx) {
    try {
        decoder.handlerAdded(ctx);
    } finally {
        encoder.handlerAdded(ctx);
    }
}
```

#### 3.4.3 不可共享

构造函数中调用 `ensureNotSharable()`，因为内部的 `ByteToMessageDecoder` 持有可变的 `cumulation` 缓冲区。

## 四、设计思想

### 4.1 编解码器本质是 Handler

Netty 编解码框架最核心的设计理念：**编解码器不是独立组件，而是 ChannelHandler 的特化**。

- `ByteToMessageDecoder extends ChannelInboundHandlerAdapter` -- 入站 Handler
- `MessageToByteEncoder extends ChannelOutboundHandlerAdapter` -- 出站 Handler
- `ByteToMessageCodec extends ChannelDuplexHandler` -- 双向 Handler

这意味着编解码器天然融入 Pipeline 体系，可以与其他 Handler（如业务逻辑 Handler）自由组合。

### 4.2 累积模式 vs 逐次模式

`ByteToMessageDecoder` 采用**累积模式**：将多次到达的字节数据累积到 `cumulation` 缓冲区，然后尝试解码。这解决了 TCP 粘包/拆包问题。

对比：`MessageToMessageDecoder` 采用**逐次模式**，每次 `channelRead` 只处理一条消息。

### 4.3 类型安全的泛型匹配

`TypeParameterMatcher` 通过运行时反射获取泛型参数的实际类型，实现零样板代码的类型匹配。开发者只需声明泛型类型参数，框架自动完成类型检查和转换。

### 4.4 资源管理的严格约定

- 编码器在 `encode()` 完成后自动 release 输入消息
- 解码器在 `channelRead()` 的 finally 块中管理 `cumulation` 生命周期
- `CodecOutputList` 通过池化减少 GC 压力
- `discardSomeReadBytes()` 在可控条件下回收已读字节

### 4.5 状态机与重入保护

`ByteToMessageDecoder` 使用三态状态机（`STATE_INIT` / `STATE_CALLING_CHILD_DECODE` / `STATE_HANDLER_REMOVED_PENDING`）处理以下边界情况：

1. **重入调用**：在 `decode()` 中触发了新的 `channelRead`
2. **Handler 移除**：在 `decode()` 过程中 Handler 被从 Pipeline 中移除
3. **连接关闭**：在解码过程中连接断开

```
  Application
      |
```

## 六、关键流程

### 6.1 完整的入站解码流程

```
1. NioEventLoop 检测到 OP_READ 事件
2. NioByteUnsafe.read() 从 SocketChannel 读取数据到 ByteBuf
3. Pipeline.fireChannelRead(ByteBuf)
4. ByteToMessageDecoder.channelRead(ctx, ByteBuf)
   |
   +-- 4a. cumulation = cumulator.cumulate(累积字节)
   +-- 4b. callDecode(ctx, cumulation, out)
   |       |
   |       +-- while (in.isReadable()):
   |       |     decode(ctx, in, out)  // 子类实现
   |       |     if (有产出) fireChannelRead(out)
   |       |     if (singleDecode) break
   |       |
   +-- 4c. 管理 cumulation 生命周期
   +-- 4d. fireChannelRead(out) 传递解码结果
5. Pipeline.fireChannelReadComplete()
6. ByteToMessageDecoder.channelReadComplete()
   +-- discardSomeReadBytes()
   +-- ctx.fireChannelReadComplete()
```

### 6.2 完整的出站编码流程

```
1. 业务代码调用 ctx.write(MyMessage)
2. Pipeline 中的 MessageToByteEncoder.write(ctx, msg, promise)
   |
   +-- 2a. acceptOutboundMessage(msg) -- 类型匹配
   +-- 2b. allocateBuffer(ctx, msg, preferDirect) -- 分配 ByteBuf
   +-- 2c. encode(ctx, msg, buf) -- 子类编码
   +-- 2d. ReferenceCountUtil.release(msg) -- 释放输入
   +-- 2e. ctx.write(buf, promise) -- 传递编码结果
3. 后续 Handler 处理（如 LengthFieldPrepender 添加长度头）
4. HeadHandler 将 ByteBuf 写入 SocketChannel
```

## 七、学习要点

1. **理解累积模式**：`ByteToMessageDecoder` 的 `cumulation` 机制是处理 TCP 粘包/拆包的核心，理解 `MERGE_CUMULATOR` 和 `COMPOSITE_CUMULATOR` 的取舍很重要。

2. **状态机设计**：三态状态机优雅地处理了重入和异步移除的边界情况，这是并发编程中的经典模式。

3. **编解码器即 Handler**：这不是一个简单的实现细节，而是 Netty 架构的核心理念。编解码器融入 Pipeline 体系，可以自由组合、替换、测试。

4. **资源管理**：Netty 的引用计数机制贯穿编解码框架，`retain()`/`release()` 的正确使用是避免内存泄漏的关键。特别注意 `readRetainedSlice()` vs `readBytes()` 的区别。

5. **CodecOutputList 的优化思路**：池化 + 延迟清理 + 环形缓冲区，是减少高频临时对象 GC 压力的通用手段。

6. **singleDecode 的使用场景**：在协议升级（如 HTTP Upgrade 到 WebSocket）时，需要确保不混合处理不同协议的消息。

7. **TypeParameterMatcher 的原理**：通过 `.getClass().getGenericSuperclass()` 获取参数化类型，再提取实际类型参数。这是 Netty 实现类型安全泛型 Handler 的基础设施。
