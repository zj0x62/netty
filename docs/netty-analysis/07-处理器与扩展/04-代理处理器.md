# 代理处理器 — ProxyHandler 源码分析

## 概述

Netty 的代理模块提供了一套统一的代理连接抽象，支持 SOCKS4、SOCKS5 和 HTTP CONNECT 三种代理协议。`ProxyHandler` 是抽象基类，封装了代理握手的通用流程，子类只需实现协议特定的编解码和消息处理逻辑。

**源码位置**: `handler-proxy/src/main/java/io/netty/handler/proxy/`

## 核心类分析

### ProxyHandler（抽象基类）

**代理状态机**:

```
handlerAdded / channelActive
        │
        ▼
  sendInitialMessage() ──► 发送初始消息到代理服务器
        │
        ▼
  channelRead() ──► handleResponse() ──┬─ return true  ──► setConnectSuccess()
                                       └─ return false ──► 等待更多响应
        │
        ▼
  连接建立 ──► 移除编解码器 ──► 写出暂存数据 ──► connectPromise.trySuccess()
```

**关键字段**:

```java
private final SocketAddress proxyAddress;           // 代理服务器地址
private volatile SocketAddress destinationAddress;   // 目标地址
private volatile long connectTimeoutMillis;          // 连接超时（默认 10s）
private PendingWriteQueue pendingWrites;             // 握手期间的暂存写队列
private boolean finished;                            // 握手是否完成
private final LazyChannelPromise connectPromise;     // 连接结果 Promise
```

**connect() 拦截**:

```java
public final void connect(ChannelHandlerContext ctx, SocketAddress remoteAddress,
        SocketAddress localAddress, ChannelPromise promise) throws Exception {
    if (destinationAddress != null) {
        promise.setFailure(new ConnectionPendingException());
        return;
    }
    destinationAddress = remoteAddress;
    ctx.connect(proxyAddress, localAddress, promise);  // 实际连接代理服务器
}
```

用户的 `connect()` 调用被拦截，实际建立的是到代理服务器的连接，目标地址被保存供后续握手使用。

**写操作暂存**:

握手完成前，所有 `write()` 调用被暂存到 `PendingWriteQueue`：

```java
public final void write(ChannelHandlerContext ctx, Object msg, ChannelPromise promise) throws Exception {
    if (finished) {
        writePendingWrites();
        ctx.write(msg, promise);
    } else {
        addPendingWrite(ctx, msg, promise);
    }
}
```

**连接超时机制**: `sendInitialMessage()` 中启动定时任务，超时后调用 `setConnectFailure()`。

### HttpProxyHandler

使用 HTTP/1.1 CONNECT 方法建立隧道。

**握手流程**:
1. 发送 `CONNECT host:port HTTP/1.1` 请求
2. 可选 `Proxy-Authorization: Basic ...` 头（Base64 编码用户名:密码）
3. 等待 `200 OK` 响应

```java
protected Object newInitialMessage(ChannelHandlerContext ctx) throws Exception {
    FullHttpRequest req = new DefaultFullHttpRequest(
            HttpVersion.HTTP_1_1, HttpMethod.CONNECT, url, Unpooled.EMPTY_BUFFER);
    req.headers().set(HttpHeaderNames.HOST, hostHeader);
    if (authorization != null) {
        req.headers().set(HttpHeaderNames.PROXY_AUTHORIZATION, authorization);
    }
    return req;
}
```

**Codec 保护**: 使用 `HttpClientCodecWrapper` 包装 `HttpClientCodec`，防止被其他 Handler（如 WebSocket Handshaker）误删。

### Socks4ProxyHandler

SOCKS4 协议代理，流程最简单：
1. 发送 `Socks4CommandRequest(CONNECT, host, port, username)`
2. 接收 `Socks4CommandResponse`，检查状态为 `SUCCESS`

仅支持用户名认证（SOCKS4a 扩展），不支持密码。

### Socks5ProxyHandler

SOCKS5 协议支持多阶段握手：

```
Client                          Proxy Server
  │                                  │
  │── InitialRequest ──────────────►│  (声明支持的认证方式)
  │                                  │
  │◄── InitialResponse ─────────────│  (选定认证方式)
  │                                  │
  │  [若需要密码认证]                 │
  │── PasswordAuthRequest ─────────►│
  │◄── PasswordAuthResponse ────────│
  │                                  │
  │  [若需要私有认证]                 │
  │── PrivateAuthRequest ──────────►│
  │◄── PrivateAuthResponse ─────────│
  │                                  │
  │── CommandRequest(CONNECT) ─────►│
  │                                  │
  │◄── CommandResponse ─────────────│
```

**动态 Decoder 替换**: 每个阶段完成后，通过 `ctx.pipeline().replace()` 替换解码器：

```java
// 初始响应后，根据认证方式替换解码器
if (resAuthMethod == Socks5AuthMethod.PASSWORD) {
    ctx.pipeline().replace(decoderName, decoderName, new Socks5PasswordAuthResponseDecoder());
    sendToProxyServer(new DefaultSocks5PasswordAuthRequest(username, password));
}
```

**地址类型处理**: `sendConnectCommand()` 根据目标地址类型选择 `IPv4`、`IPv6` 或 `DOMAIN`。

## 设计思想

1. **模板方法模式**: `ProxyHandler` 定义了握手骨架（`addCodec`、`newInitialMessage`、`handleResponse`），子类实现协议细节
2. **PendingWriteQueue 缓冲**: 握手期间的写操作被暂存，握手成功后按序写出，保证数据不丢失
3. **统一的异常处理**: 所有异常被包装为 `ProxyConnectException`，携带协议、认证方式、代理地址、目标地址等上下文
4. **connectPromise 解耦**: 通过 `Future<Channel>` 模式，调用方可以异步等待代理连接建立

## 关键流程

```
用户调用 channel.connect(target)
    │
    ▼
ProxyHandler.connect() ──► 保存 target，实际连接 proxyAddress
    │
    ▼
channelActive() ──► sendInitialMessage()
    │               ──► newInitialMessage() [子类实现]
    │               ──► 启动连接超时定时器
    ▼
channelRead(proxyResponse)
    │
    ▼
handleResponse() [子类实现]
    │
    ├─ return false ──► 等待更多响应
    │
    └─ return true  ──► setConnectSuccess()
                        ├─ 移除编解码器
                        ├─ 触发 ProxyConnectionEvent
                        ├─ 写出暂存数据
                        └─ connectPromise.trySuccess(channel)
```

## 学习要点

- **代理连接的透明性**: 对上层业务而言，代理连接建立后的 Channel 行为与直连完全一致，编解码器被移除后不再有代理协议的痕迹
- **PendingWriteQueue 的使用**: 这是 Netty 提供的线程安全写队列，专门用于"先缓存后批量写出"的场景
- **LazyChannelPromise**: 内部类继承 `DefaultPromise`，延迟获取 `EventExecutor`，解决了 `handlerAdded` 时 `ctx` 可能尚未就绪的问题
- **codecWrapper 的防御设计**: 用包装类隔离内部 Codec，防止被外部 Handler 意外移除，体现了"防御性编程"思想
