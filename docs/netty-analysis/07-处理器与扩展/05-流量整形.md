# 流量整形 — TrafficShapingHandler 源码分析

## 概述

Netty 的流量整形模块提供了基于令牌桶思想的带宽限制能力，可以对读/写操作进行速率控制。支持单 Channel 级别和全局级别的流量整形，适用于限流、带宽管理、防突发等场景。

**源码位置**: `handler/src/main/java/io/netty/handler/traffic/`

## 核心类分析

### AbstractTrafficShapingHandler

抽象基类，继承 `ChannelDuplexHandler`，定义了流量整形的核心框架。

**关键参数**:

| 参数 | 含义 | 默认值 |
|------|------|--------|
| `writeLimit` | 写速率限制（bytes/s），0 表示不限 | 0 |
| `readLimit` | 读速率限制（bytes/s），0 表示不限 | 0 |
| `checkInterval` | 统计周期（ms） | 1000 |
| `maxTime` | 最大等待时间上限（ms） | 15000 |
| `maxWriteDelay` | 写延迟上限（ms），超过则暂停写 | 4000 |
| `maxWriteSize` | 写缓冲区大小上限（bytes） | 4MB |

**读限流机制** (`channelRead()`):

```java
long wait = trafficCounter.readTimeToWait(size, readLimit, maxTime, now);
if (wait >= MINIMAL_WAIT) {  // 至少 10ms
    config.setAutoRead(false);                    // 暂停读取
    channel.attr(READ_SUSPENDED).set(true);
    ctx.executor().schedule(reopenTask, wait, TimeUnit.MILLISECONDS);  // 延迟恢复
}
ctx.fireChannelRead(msg);  // 当前消息仍然向后传播
```

读限流通过关闭 `autoRead` 实现——暂停从底层 Socket 读取数据，定时恢复。

**写限流机制** (`write()`):

```java
long wait = trafficCounter.writeTimeToWait(size, writeLimit, maxTime, now);
if (wait >= MINIMAL_WAIT) {
    submitWrite(ctx, msg, size, wait, now, promise);  // 延迟写出
    return;
}
submitWrite(ctx, msg, size, 0, now, promise);  // 立即写出（但可能排队）
```

写限流通过延迟调度实现——将消息暂存到队列，定时批量发送。

**UserDefinedWritability**: 使用 `ChannelOutboundBuffer.setUserDefinedWritability(index, boolean)` 控制 Channel 的可写状态，让上游 Handler 感知到背压。

### TrafficCounter

流量统计核心，负责计算读/写的吞吐量和限流延迟。

**关键算法** — `readTimeToWait()` / `writeTimeToWait()`:

```java
// 核心公式：等待时间 = 已传输字节 * 1000 / 速率限制 - 已过时间 + 历史延迟
long time = sum * 1000 / limitTraffic - interval + pastDelay;
```

- `sum`: 当前统计周期内已传输的字节数
- `limitTraffic`: 速率限制（bytes/s）
- `interval`: 距上次统计的时间间隔（ms）
- `pastDelay`: 上个周期累积的延迟

当间隔不够长时，会合并上个周期的数据进行计算，避免短时间内的突发误判。

**周期性统计**: 通过 `ScheduledExecutorService.scheduleAtFixedRate()` 定期调用 `resetAccounting()`，计算吞吐量并重置计数器。

### ChannelTrafficShapingHandler

单 Channel 级别的流量整形，Pipeline Coverage 为 "one"（每个 Channel 需要独立实例）。

**延迟写出机制**:

```java
void submitWrite(ChannelHandlerContext ctx, Object msg, long size,
        long delay, long now, ChannelPromise promise) {
    synchronized (this) {
        if (delay == 0 && messagesQueue.isEmpty()) {
            ctx.write(msg, promise);  // 无延迟且队列为空，直接写出
            return;
        }
        messagesQueue.addLast(new ToSend(delay + now, msg, promise));
        queueSize += size;
        checkWriteSuspend(ctx, delay, queueSize);
    }
    ctx.executor().schedule(() -> sendAllValid(ctx, futureNow), delay, TimeUnit.MILLISECONDS);
}
```

消息按计划时间放入 `ArrayDeque`，定时任务触发时批量发送所有到期消息。

### GlobalTrafficShapingHandler

全局流量整形，Pipeline Coverage 为 "all"（所有 Channel 共享一个实例），标注 `@Sharable`。

**PerChannel 结构**: 使用 `ConcurrentMap<Integer, PerChannel>` 管理每个 Channel 的消息队列：

```java
private final ConcurrentMap<Integer, PerChannel> channelQueues = new ConcurrentHashMap<>();
private final AtomicLong queuesSize = new AtomicLong();  // 全局队列总大小
```

每个 `PerChannel` 维护独立的 `messagesQueue`、`queueSize`、`lastWriteTimestamp`。

**全局写限制**: `maxGlobalWriteSize`（默认 400MB）控制所有 Channel 队列的总大小，超过后通过 `setUserDefinedWritability(ctx, false)` 暂停所有 Channel 的写入。

### 三种 Handler 对比

| 特性 | Channel | Global | GlobalChannel |
|------|---------|--------|---------------|
| 作用范围 | 单 Channel | 全局共享 | 单 Channel（全局统计） |
| Pipeline Coverage | one | all (@Sharable) | one |
| Writability Index | 1 | 2 | 3 |
| TrafficCounter | per channel | 全局共享 | per channel（全局计数） |
| 适用场景 | 单连接限流 | 服务器总带宽限制 | 单连接限流（全局公平调度） |

## 设计思想

1. **延迟调度替代阻塞**: 不使用 `Thread.sleep()` 阻塞线程，而是将消息暂存后通过 `EventLoop.schedule()` 延迟发送，不占用 IO 线程
2. **统计周期与限流精度的权衡**: `checkInterval` 越小精度越高但开销越大，文档建议 5-10 分钟为上限
3. **UserDefinedWritability 背压**: 利用 Netty 的可写性机制实现反压，上游 Handler 可通过 `channelWritabilityChanged()` 感知限流状态
4. **synchronized 保证写顺序**: 消息队列操作使用 `synchronized`，保证写出顺序与入队顺序一致

## 关键流程

```
write(ctx, msg, promise)
    │
    ▼
calculateSize(msg) ──► 获取消息字节数
    │
    ▼
trafficCounter.writeTimeToWait(size, writeLimit, maxTime, now)
    │
    ├─ wait < 10ms ──► submitWrite(delay=0) ──► 直接写出或入队
    │
    └─ wait >= 10ms ──► submitWrite(delay=wait)
                          │
                          ▼
                     入队 messagesQueue
                     schedule(sendAllValid, delay)
                          │
                          ▼
                     定时触发 ──► 批量发送到期消息
```

## 学习要点

- **限流延迟计算公式**: `time = bytes * 1000 / limit - interval + pastDelay`，本质是"当前周期应传字节 vs 实际已传字节"的差值换算为等待时间
- **最小等待阈值**: `MINIMAL_WAIT = 10ms`，低于此值不做限流，避免频繁调度的开销超过限流收益
- **maxTime 的保护作用**: 限制单次最大等待时间，防止因大量突发数据导致过长延迟，避免连接超时
- **configure() 的 best effort 语义**: 参数变更只影响新流量，已调度的消息不受影响，这是分布式系统中常见的"最终一致性"思路
