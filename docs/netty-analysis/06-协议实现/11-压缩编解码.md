# Netty 压缩编解码器源码分析

## 1. 概述

Netty 的 `codec-compression` 模块提供了多种压缩算法的编解码器实现，将压缩/解压逻辑无缝集成到 Netty 的 ChannelPipeline 中。该模块支持以下压缩算法：

| 算法 | 压缩比 | 速度 | 适用场景 |
|------|--------|------|----------|
| **Zlib/Gzip/Deflate** | 中高 | 中等 | HTTP 传输、通用压缩 |
| **Brotli** | 高 | 慢 | Web 静态资源、HTTP Content-Encoding |
| **Snappy** | 中 | 极快 | 实时通信、低延迟场景 |
| **LZ4** | 中 | 极快 | 日志压缩、大数据管道 |
| **Zstd** | 高 | 快 | 通用压缩、数据库/存储 |
| **Bzip2** | 高 | 慢 | 存储压缩、对速度不敏感的场景 |
| **FastLz** | 中 | 极快 | 轻量级嵌入式场景 |
| **LZF** | 中 | 快 | JSON 数据压缩 |
| **LZMA** | 极高 | 极慢 | 存储归档 |

核心设计模式统一：**编码器继承 `MessageToByteEncoder<ByteBuf>`，解码器继承 `ByteToMessageDecoder`**。

## 3. 核心类分析

### 3.1 Zlib 家族 (Zlib/Gzip/Deflate)

Zlib 是最复杂的压缩实现，提供两套实现并由 `ZlibCodecFactory` 统一管理。

**ZlibWrapper 枚举** 定义了四种容器格式：

```java
public enum ZlibWrapper {
    ZLIB,           // RFC 1950 - 标准 Zlib 格式
    GZIP,           // RFC 1952 - Gzip 格式
    NONE,           // 纯 Deflate 流，无头尾
    ZLIB_OR_NONE    // 仅用于解码，自动检测
}
```

**JdkZlibEncoder** 关键设计：
- 基于 `java.util.zip.Deflater`，零额外依赖
- GZIP 模式下手动维护 CRC32 校验和 GZIP 头部（10 字节魔数）
- 通过 `Deflater.SYNC_FLUSH` 实现流式压缩，每批数据立即输出
- 内部缓冲区管理：使用堆内存 `heapBuffer`，通过 `MAX_INITIAL_OUTPUT_BUFFER_SIZE`（默认 64KB）控制初始分配

```java
// 编码核心逻辑
protected void encode(ChannelHandlerContext ctx, ByteBuf uncompressed, ByteBuf out) {
    if (uncompressed.hasArray()) {
        encodeSome(uncompressed, out);  // 直接操作底层数组，零拷贝
    } else {
        // 堆外内存需先拷贝到堆内存
        ByteBuf heapBuf = ctx.alloc().heapBuffer(heapBufferSize);
        // ... 拷贝后调用 encodeSome
    }
}
```

**JdkZlibDecoder** 关键设计：
- GZIP 解码使用状态机（`GzipState` 枚举）处理头部的复杂可选字段（FEXTRA、FNAME、FCOMMENT、FHCRC）
- 支持 `ZLIB_OR_NONE` 模式：延迟到首 2 字节到达后才决定 `Inflater` 参数
- 支持 `decompressConcatenated`：解码串联的多个 GZIP 流
- `maxAllocation` 机制防止解压炸弹（decompression bomb）

**ZlibCodecFactory** 工厂策略：
- 通过 `io.netty.noJdkZlibDecoder` / `io.netty.noJdkZlibEncoder` 系统属性切换实现
- 当需要自定义 `windowBits` 或 `memLevel` 时，自动回退到 JZlib（JDK 不支持这些参数）
- JZlib 需要额外依赖 `com.jcraft.jzlib`

### 3.2 Snappy

Snappy 采用**帧格式**（framing format），将数据切分为独立的块。

**SnappyFrameEncoder**：
- 首次写入时输出流标识：`[0xff, 0x06, 0x00, 0x00, 's','N','a','P','p','Y']`
- 数据按 `sliceSize`（默认 32KB）分块压缩
- 小于 18 字节的数据不压缩，直接作为 `UNCOMPRESSED_DATA` 块输出
- 压缩块格式：`[chunk_type(1) | chunk_length(3) | checksum(4) | compressed_data]`

**SnappyFrameDecoder**：
- 使用 `ChunkType` 枚举区分 5 种块类型
- 校验和默认关闭（性能考虑），可通过构造参数启用
- 块大小限制：压缩块最大 16MB，解压后最大 64KB

### 3.3 LZ4

LZ4 是速度优先的压缩算法，Netty 使用 lz4-java 库。

**Lz4FrameEncoder**：
- 内部维护一个 `blockSize`（默认 64KB）的缓冲区
- 数据先填充到缓冲区，满时才触发压缩
- 自动判断：压缩后反而更大时，直接存储原始数据（`BLOCK_TYPE_NON_COMPRESSED`）
- 每个块包含完整的头部：`[MAGIC(8) | TOKEN(1) | COMPRESSED_LEN(4) | DECOMPRESSED_LEN(4) | CHECKSUM(4) | DATA]`

```java
// 智能选择压缩/存储
if (compressedLength >= flushableBytes) {
    blockType = BLOCK_TYPE_NON_COMPRESSED;
    compressedLength = flushableBytes;
    out.setBytes(idx + HEADER_LENGTH, buffer, buffer.readerIndex(), flushableBytes);
}
```

**Lz4FrameDecoder**：
- 使用状态机（`INIT_BLOCK -> DECOMPRESS_DATA`）逐块解码
- 通过 `maxDecompressedLength`（默认 32MB）限制解压大小，防止内存溢出
- 压缩级别从 token 字段的低 4 位提取

### 3.4 Zstd

Zstd 是 Facebook 开发的新一代压缩算法，在压缩比和速度之间取得优秀平衡。

**ZstdEncoder**：
- 使用 `zstd-jni` 库（`com.github.luben.zstd`）
- 分块压缩策略，`blockSize` 控制每块大小
- 使用 `Zstd.compressBound()` 精确估算输出缓冲区
- 优先使用 direct buffer

**ZstdDecoder**：
- 使用 `ZstdInputStreamNoFinalizer` 流式解压
- 通过 `MutableByteBufInputStream` 适配 ByteBuf 到 InputStream
- `maxWindowLog` 参数限制解压窗口大小（默认 27，对应 128MB），防止内存放大攻击
- 支持大块数据分批 `fireChannelRead`，避免单次分配过大缓冲区

### 3.5 Bzip2

Bzip2 是纯 Java 实现，无需外部依赖。

**Bzip2Encoder**：
- 使用状态机管理编码流程：`INIT -> INIT_BLOCK -> WRITE_DATA -> CLOSE_BLOCK`
- `Bzip2BlockCompressor` 负责单个块的压缩
- 块大小以 100KB 为单位（1-9 倍），默认 900KB
- 使用 `Bzip2BitWriter` 进行比特级写入
- 流结束时写入 `END_OF_STREAM_MAGIC` 和全局 CRC

**Bzip2Decoder**：
- 状态机最复杂，包含 10 个状态
- 解码流程：读取魔数 -> 解析块头部 -> Huffman 解码 -> BWT 逆变换 -> RLE 解压
- `Bzip2BitReader` 提供比特级读取能力
- 每个块独立校验 CRC，流结束时校验合并 CRC

## 4. 设计思想

### 4.1 统一的编解码器模式

所有压缩编解码器遵循相同的继承模式：
- **编码器**：`extends MessageToByteEncoder<ByteBuf>` -- 输入 `ByteBuf`，输出压缩后的 `ByteBuf`
- **解码器**：`extends ByteToMessageDecoder` -- 输入压缩的 `ByteBuf`，输出解压后的 `ByteBuf`

这种一致性使得压缩 Handler 可以像其他编解码器一样直接插入 Pipeline。

### 4.2 策略模式与工厂模式结合

`ZlibCodecFactory` 体现了策略模式：
- 通过系统属性选择 JDK 或 JZlib 实现
- 根据参数复杂度自动选择最佳实现
- 调用方无需关心底层实现差异

### 4.3 防御性内存管理

解码器普遍采用多层防护：
- `maxAllocation` / `maxDecompressedLength` 限制单次解压输出大小
- `maxWindowLog`（Zstd）限制解压窗口，防止内存放大攻击
- 分批 `fireChannelRead` 避免单次分配过大缓冲区
- `maxForwardBytes` 阈值控制前推时机

### 4.4 状态机驱动的流式解码

复杂的解码器（GZIP、Bzip2、LZ4）都使用状态机模式：
- 每次 `decode()` 调用尝试推进状态
- 数据不足时保存状态并返回，等待更多数据
- 遇到错误时转入 `CORRUPTED` 状态，后续数据直接丢弃

### 4.5 校验和的可选性

Snappy 和 LZ4 解码器默认**禁用**校验和验证：
- 构造参数 `validateChecksums` 控制
- 默认关闭以提升性能
- 在不可信网络环境下建议开启

## 5. 模块交互

```
                    Pipeline 集成
                    ============

  ┌──────────┐    ┌──────────────┐    ┌──────────────┐
  │  业务    │───▶│ 压缩编码器   │───▶│  网络传输    │
  │  Handler │    │ (Encoder)    │    │              │
  └──────────┘    └──────────────┘    └──────────────┘

  ┌──────────┐    ┌──────────────┐    ┌──────────────┐
  │  业务    │◀───│ 压缩解码器   │◀───│  网络传输    │
  │  Handler │    │ (Decoder)    │    │              │
  └──────────┘    └──────────────┘    └──────────────┘

  Pipeline 配置示例:
  pipeline.addLast(new ZstdEncoder());
  pipeline.addLast(new ZstdDecoder());
```

编解码器与 Netty 核心组件的交互：
- **ByteBuf**：所有编解码器的操作对象，利用其 `hasArray()` 判断堆内/堆外内存以选择零拷贝路径
- **ChannelHandlerContext**：通过 `ctx.alloc()` 获取分配器，通过 `ctx.fireChannelRead()` 传递解压结果
- **ChannelPromise**：编码器的 `close()` 方法返回 `ChannelFuture`，支持异步关闭通知
- **EncoderUtil.closeAfterFinishEncode()**：统一的超时关闭机制，防止编码完成回调丢失

## 6. 关键流程

### 6.1 Zlib/Gzip 编码流程

```
JdkZlibEncoder.encode(ByteBuf in, ByteBuf out)
  │
  ├── finished? ──是──▶ 直接透传原始数据
  │
  ├── in.hasArray()? ──是──▶ encodeSome(in, out) [零拷贝]
  │                      否──▶ 先拷贝到堆内存再 encodeSome
  │
  └── encodeSome(in, out):
        ├── 首次写入? ──是──▶ 写 GZIP 头部 (10字节魔数)
        ├── CRC32.update(原始数据)
        ├── deflater.setInput(data)
        └── 循环 deflater.deflate() 直到 needsInput()
```

### 6.2 Snappy 帧编码流程

```
SnappyFrameEncoder.encode(ByteBuf in, ByteBuf out)
  │
  ├── started? ──否──▶ 写入流标识 "sNaPpY"
  │
  └── dataLength > 18?
        │
        ├── 是: 循环按 sliceSize 分块
        │     ├── 写 chunk_length 占位 (3字节)
        │     ├── 写 checksum (4字节)
        │     ├── snappy.encode(slice, out)
        │     └── 回填 chunk_length
        │
        └── 否: 写入 UNCOMPRESSED_DATA 块
              └── [type=1 | length | checksum | raw_data]
```

### 6.3 LZ4 编码流程

```
Lz4FrameEncoder.encode(ByteBuf in, ByteBuf out)
  │
  ├── 数据追加到内部 buffer
  │
  └── buffer 满?
        │
        └── 是: flushBufferedData(out)
              ├── 计算 checksum
              ├── compressor.compress(buffer, outNioBuffer)
              ├── 压缩后更大? ──是──▶ 存储原始数据
              │                   否──▶ 存储压缩数据
              └── 写块头部: [MAGIC | TOKEN | COMP_LEN | DEC_LEN | CRC]
```

### 6.4 Bzip2 解码状态机

```
Bzip2Decoder 状态转换:
  INIT ──▶ INIT_BLOCK ──▶ INIT_BLOCK_PARAMS ──▶ RECEIVE_HUFFMAN_USED_MAP
                                                            │
    EOF ◀─────────────────────────────────────────────────── ▼
    (校验CRC)     RECEIVE_SELECTORS ◀── RECEIVE_SELECTORS_NUMBER
                      │
                      ▼
              RECEIVE_HUFFMAN_LENGTH ──▶ DECODE_HUFFMAN_DATA
                                           │
                                           ▼
                                      返回解压数据
                                      (状态回到 INIT_BLOCK)
```

## 7. 学习要点

### 7.1 编解码器模式
- 理解 `MessageToByteEncoder<ByteBuf>` 和 `ByteToMessageDecoder` 的职责划分
- 掌握 `encode()` 和 `decode()` 方法的调用时机与参数含义
- 理解 `allocateBuffer()` 在编码器中的作用

### 7.2 状态机设计
- 复杂协议解析使用枚举定义状态，`switch` 驱动状态转换
- 数据不足时保存状态并 `return`，等待下次调用
- 错误状态（`CORRUPTED`）确保后续数据被正确丢弃

### 7.3 内存安全
- 压缩/解压缓冲区大小必须有上限，防止 OOM
- `maxAllocation`、`maxDecompressedLength`、`maxWindowLog` 是关键防护参数
- 分批输出（`fireChannelRead`）比单次大块输出更安全

### 7.4 零拷贝优化
- `ByteBuf.hasArray()` 判断是否可直接操作底层数组
- 堆外内存需要先拷贝到堆内存才能传给 JDK/第三方库
- `internalNioBuffer()` 避免额外的 `ByteBuffer` 分配

### 7.5 校验和策略
- 校验和验证是可选的性能/安全权衡点
- GZIP 的 CRC32 是协议强制要求，不可跳过
- Snappy/LZ4 的校验和默认关闭，可按需启用

### 7.6 实现选择指南
- 无外部依赖：JdkZlib（Zlib/Gzip/Deflate）、Bzip2、FastLz、LZF
- 最快压缩/解压：Snappy、LZ4、FastLz
- 最高压缩比：Bzip2、LZMA、Brotli
- 综合最优：Zstd（压缩比高、速度快、可配置）
