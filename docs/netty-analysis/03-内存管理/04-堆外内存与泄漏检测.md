# Netty 堆外内存操作与资源泄漏检测深度分析

> **前置知识**：先读 01-01 ByteBuf 体系；JVM 内存/GC 基础。

## 一、概述

Netty 的高性能网络通信很大程度上依赖于对堆外（off-heap）内存的直接操作能力。与 JVM 堆内存相比，堆外内存不受 GC 管理，可以减少垃圾回收带来的延迟抖动，同时支持零拷贝的 I/O 操作。然而，堆外内存也带来了两个核心挑战：

1. **内存操作的平台差异性**：不同 JDK 版本和操作系统对底层内存访问 API 的支持各不相同，需要一套完善的平台适配层。
2. **内存泄漏的隐蔽性**：堆外内存不经过 GC，如果忘记释放就会造成内存泄漏，且难以定位。

Netty 通过三层架构解决这两个问题：
- **平台适配层**（`PlatformDependent0` / `PlatformDependent`）：统一封装 `sun.misc.Unsafe` 等底层 API，屏蔽平台差异。
- **堆外内存操作层**（`UnsafeByteBufUtil`）：基于平台适配层实现高效的多字节读写操作。
- **资源泄漏检测层**（`ResourceLeakDetector` / `ResourceLeakTracker`）：通过弱引用 + 采样机制在开发阶段捕获泄漏。

```
┌─────────────────────────────────────────────────────────────────┐
│                      ByteBuf (业务层)                            │
├─────────────────────────────────────────────────────────────────┤
│  UnsafeByteBufUtil   │   ResourceLeakDetector                   │
│  (堆外内存读写操作)    │   (资源泄漏检测)                          │
├──────────────────────┴─────────────────────────────────────────┤
│                   PlatformDependent                              │
│            (平台适配统一入口，内存分配/释放)                        │
├─────────────────────────────────────────────────────────────────┤
│                   PlatformDependent0                             │
│        (sun.misc.Unsafe 封装，底层原子操作)                       │
├─────────────────────────────────────────────────────────────────┤
│  CleanerJava9  │ CleanerJava6 │ CleanerJava24Linker │ CleanerJava25  │
│  (JDK 9+清理)  │ (JDK 8清理)  │ (JDK 24+ Linker)    │ (JDK 25+ Arena)│
└─────────────────────────────────────────────────────────────────┘
```

## 二、核心类分析

### 2.1 PlatformDependent0 — Unsafe 底层封装

**文件位置**：`common/src/main/java/io/netty/util/internal/PlatformDependent0.java`

`PlatformDependent0` 是 Netty 访问 `sun.misc.Unsafe` 的最底层封装类。它通过反射获取 `Unsafe` 实例，并提供一系列直接操作内存地址的方法。

#### 2.1.1 Unsafe 实例的获取

```java
static final Unsafe UNSAFE;
```

在静态初始化块中，通过 `AccessController.doPrivileged` 特权操作获取 `Unsafe.theUnsafe` 字段：

```java
final Field unsafeField = Unsafe.class.getDeclaredField("theUnsafe");
Throwable cause = ReflectionUtil.trySetAccessible(unsafeField, false);
if (cause != null) {
    return cause;
}
return unsafeField.get(null);
```

获取到 Unsafe 实例后，还会验证关键方法的可用性：
- `copyMemory(Object, long, Object, long, long)`：内存拷贝
- 对于 JDK 23+，额外验证 `objectFieldOffset`、`allocateMemory`、`freeMemory` 等方法
- 对于 JDK 23+，还会实际调用 `allocateMemory/putLong/freeMemory` 来验证内存访问不会抛出 `UnsupportedOperationException`

#### 2.1.2 关键常量的初始化

```java
private static final long ADDRESS_FIELD_OFFSET;       // Buffer.address 字段偏移量
private static final long BYTE_ARRAY_BASE_OFFSET;      // byte[] 数组起始偏移量
private static final long INT_ARRAY_BASE_OFFSET;       // int[] 数组起始偏移量
private static final long INT_ARRAY_INDEX_SCALE;        // int[] 元素间距
private static final long LONG_ARRAY_BASE_OFFSET;      // long[] 数组起始偏移量
private static final long LONG_ARRAY_INDEX_SCALE;       // long[] 元素间距
private static final MethodHandle DIRECT_BUFFER_CONSTRUCTOR; // DirectByteBuffer 构造器
```

- `ADDRESS_FIELD_OFFSET`：通过 Unsafe 获取 `java.nio.Buffer.address` 字段的偏移量，用于读取 DirectByteBuffer 的原生内存地址。如果此字段不可访问，则整个 Unsafe 机制不可用。
- `BYTE_ARRAY_BASE_OFFSET`：`byte[]` 数组第一个元素的内存偏移量，所有对数组的 Unsafe 操作都基于此偏移量。
- `DIRECT_BUFFER_CONSTRUCTOR`：通过反射获取 `DirectByteBuffer(long, int)` 构造器的 MethodHandle，用于从原生地址创建 DirectByteBuffer。JDK 21+ 的构造器签名变更为 `(long, long)`。

#### 2.1.3 堆外内存分配与释放

```java
static ByteBuffer allocateDirectNoCleaner(int capacity) {
    return newDirectBuffer(UNSAFE.allocateMemory(Math.max(1, capacity)), capacity);
}

static ByteBuffer reallocateDirectNoCleaner(ByteBuffer buffer, int capacity) {
    return newDirectBuffer(UNSAFE.reallocateMemory(directBufferAddress(buffer), capacity), capacity);
}
```

- `allocateDirectNoCleaner`：直接调用 `Unsafe.allocateMemory` 分配原生内存，然后通过 `DIRECT_BUFFER_CONSTRUCTOR` 包装为 `DirectByteBuffer`。注意 `Math.max(1, capacity)` 是因为 POSIX `malloc(0)` 的行为不一致（可能返回 NULL 或有效指针）。
- `reallocateDirectNoCleaner`：调用 `Unsafe.reallocateMemory` 重新分配内存，用于 ByteBuf 的动态扩容。

#### 2.1.4 原生内存地址读写

所有对原生地址的读写操作直接委托给 Unsafe：

```java
static byte getByte(long address)      { return UNSAFE.getByte(address); }
static short getShort(long address)    { return UNSAFE.getShort(address); }
static int getInt(long address)        { return UNSAFE.getInt(address); }
static long getLong(long address)      { return UNSAFE.getLong(address); }
static void putByte(long address, byte value)   { UNSAFE.putByte(address, value); }
static void putShort(long address, short value) { UNSAFE.putShort(address, value); }
static void putInt(long address, int value)     { UNSAFE.putInt(address, value); }
static void putLong(long address, long value)   { UNSAFE.putLong(address, value); }
```

对堆上数组的读写通过基础偏移量计算地址：

```java
static byte getByte(byte[] data, int index) {
    return UNSAFE.getByte(data, BYTE_ARRAY_BASE_OFFSET + index);
}
```

#### 2.1.5 内存拷贝与 SafePoint 轮询

```java
private static final long UNSAFE_COPY_THRESHOLD = 1024L * 1024L; // 1MB

static void copyMemory(long srcAddr, long dstAddr, long length) {
    if (javaVersion() <= 8) {
        copyMemoryWithSafePointPolling(srcAddr, dstAddr, length);
    } else {
        UNSAFE.copyMemory(srcAddr, dstAddr, length);
    }
}

private static void copyMemoryWithSafePointPolling(long srcAddr, long dstAddr, long length) {
    while (length > 0) {
        long size = Math.min(length, UNSAFE_COPY_THRESHOLD);
        UNSAFE.copyMemory(srcAddr, dstAddr, size);
        length -= size;
        srcAddr += size;
        dstAddr += size;
    }
}
```

**设计意图**：JDK 8 中 `Unsafe.copyMemory` 可能长时间不返回，导致 JVM 无法在 SafePoint 进行 GC 或偏向锁撤销。因此在 JDK 8 中将大块拷贝拆分为每 1MB 一小块，允许 JVM 在间隙中插入 SafePoint。JDK 9+ 修复了此问题（JDK-8149596），可以直接调用。

#### 2.1.6 DirectByteBuffer 地址获取

```java
static long directBufferAddress(ByteBuffer buffer) {
    if (hasUnsafe()) {
        return getLong(buffer, ADDRESS_FIELD_OFFSET);
    }
    if (hasMemorySegmentAddressOfBuffer()) {
        return (long) MEMORY_SEGMENT_ADDRESS_OF_BUFFER.invokeExact((Buffer) buffer) - buffer.position();
    }
    throw new IllegalStateException("No address access method");
}
```

两种路径：
- **Unsafe 路径**：通过 `ADDRESS_FIELD_OFFSET` 直接读取 `Buffer.address` 字段
- **MemorySegment 路径**（JDK 22+）：通过 `MemorySegment.ofBuffer(buffer).address()` 获取，需要减去 `buffer.position()` 因为 MemorySegment 返回的是当前位置的地址

#### 2.1.7 JDK 版本与 Unsafe 可用性判断

```java
private static Throwable explicitNoUnsafeCause0() {
    // JDK 25+ 默认禁用 Unsafe（JEP 471/498）
    if (!explicitProperty && unspecified.equals(unsafeMemoryAccess) && javaVersion() >= 25) {
        noUnsafe = true;
    }
    // sun.misc.unsafe.memory.access 非 "allow" 时禁用
    else if (!("allow".equals(unsafeMemoryAccess) || unspecified.equals(unsafeMemoryAccess))) {
        noUnsafe = true;
    }
}
```

Netty 在 JDK 25+ 中默认禁用 Unsafe（因为 JEP 471 移除了部分 Unsafe 方法，JEP 498 使内存访问警告默认开启），转而使用 `MemorySegment` API。

#### 2.1.8 Unaligned 访问检测

```java
private static final boolean UNALIGNED;
```

初始化时尝试读取 `java.nio.Bits.UNALIGNED` 字段（JDK 9+ 为大写，JDK 8 为小写），如果无法获取则根据 CPU 架构推断：

```java
unaligned = arch.matches("^(i[3-6]86|x86(_64)?|x64|amd64)$");
```

x86/x64 架构天然支持非对齐内存访问，其他架构（如 ARM、SPARC）可能因非对齐访问导致 Bus Error。

#### 2.1.9 数组比较与哈希码的 Unsafe 加速

```java
static boolean equals(byte[] bytes1, int startPos1, byte[] bytes2, int startPos2, int length) {
    // 每次比较 8 字节（long），剩余按 4/2/1 字节处理
    for (long i = baseOffset1 - 8 + length; i >= end; i -= 8) {
        if (UNSAFE.getLong(bytes1, i) != UNSAFE.getLong(bytes2, i + diff)) {
            return false;
        }
    }
}
```

通过 Unsafe 的 `getLong` 每次比较 8 字节，比逐字节比较快 8 倍。常量时间比较 `equalsConstantTime` 则通过 OR 运算累积所有差异，避免时序攻击。

### 2.2 PlatformDependent — 平台适配统一入口

**文件位置**：`common/src/main/java/io/netty/util/internal/PlatformDependent.java`

`PlatformDependent` 是面向上层的统一入口类，封装了 `PlatformDependent0` 的所有功能，并增加了内存计数、Cleaner 选择、平台检测等高层逻辑。

#### 2.2.1 堆外内存限额管理

```java
private static final AtomicLong DIRECT_MEMORY_COUNTER;
private static final long DIRECT_MEMORY_LIMIT;
```

通过 `-Dio.netty.maxDirectMemory` 控制 Netty 管理的堆外内存上限：
- `< 0`（默认）：使用 `estimateMaxDirectMemory()` 推算的值
- `== 0`：不使用 Cleaner，不限制 Netty 内存（由 JDK 管理）
- `> 0`：指定具体上限

```java
static void incrementMemoryCounter(int capacity) {
    if (DIRECT_MEMORY_COUNTER != null) {
        long newUsedMemory = DIRECT_MEMORY_COUNTER.addAndGet(capacity);
        if (newUsedMemory > DIRECT_MEMORY_LIMIT) {
            DIRECT_MEMORY_COUNTER.addAndGet(-capacity);
            throw new OutOfDirectMemoryError("failed to allocate " + capacity + " byte(s)...");
        }
    }
}
```

每次分配堆外内存时调用 `incrementMemoryCounter`，超过限额时抛出 `OutOfDirectMemoryError`。这是 Netty 对 JDK `MaxDirectMemorySize` 的补充保护机制。

#### 2.2.2 Cleaner 选择策略

```java
private static final Cleaner CLEANER;
private static final Cleaner LEGACY_CLEANER;
```

Cleaner 的选择遵循以下优先级：

```
非 Android 环境：
  JDK >= 9:
    1. CleanerJava9          (Unsafe.invokeCleaner)
    2. CleanerJava24Linker    (JDK 24+ Linker API 调用 libc malloc/free)
    3. CleanerJava25          (JDK 25+ Arena ofShared)
    4. NOOP                   (兜底)
  JDK < 9:
    1. CleanerJava6           (sun.misc.Cleaner)
    2. NOOP

CLEANER 最终选择：
  maxDirectMemory != 0 && hasUnsafe() && hasDirectBufferNoCleanerConstructor():
    DirectCleaner    (直接 Unsafe.allocateMemory/freeMemory)
  否则:
    LEGACY_CLEANER
```

`DirectCleaner` 是性能最优的选择，因为它直接调用 `Unsafe.allocateMemory` / `freeMemory`，不经过 JDK 的 DirectByteBuffer Cleaner 机制。`LEGACY_CLEANER` 则适用于无法直接控制原生内存的场景。

#### 2.2.3 堆外内存分配入口

```java
public static CleanableDirectBuffer allocateDirect(int capacity, boolean permitExpensiveClean) {
    if (!IGNORE_EXPENSIVE_CLEAN && !permitExpensiveClean && CLEANER.hasExpensiveClean()) {
        return NOOP.allocate(capacity); // 回退到 JDK 管理的 DirectByteBuffer
    }
    return CLEANER.allocate(capacity);
}
```

`permitExpensiveClean` 参数用于区分池化和非池化分配器：
- 池化分配器（PooledByteBufAllocator）：`permitExpensiveClean = true`，使用高性能 Cleaner
- 非池化分配器（UnpooledByteBufAllocator）：`permitExpensiveClean = false`，如果 Cleaner 代价高昂则回退到 JDK 的 GC 管理

这主要影响 `CleanerJava25`（基于 `Arena.ofShared()`），其 `clean()` 操作依赖跨线程握手（inter-thread handshake），代价较高。

#### 2.2.4 多字节访问策略

```java
public static boolean useVarHandleForMultiByteAccess() {
    return !isUnaligned() && VAR_HANDLE;
}

public static boolean canUnalignedAccess() {
    return isUnaligned() || VAR_HANDLE;
}
```

多字节访问的策略决策：
1. 平台支持非对齐访问（x86/x64）：使用 `Unsafe`，最快速
2. 不支持非对齐访问但有 `VarHandle`：使用 `VarHandle`，由 JVM 处理对齐和字节序
3. 都不可用：手动逐字节拼装

### 2.3 UnsafeByteBufUtil — 堆外内存读写操作

**文件位置**：`buffer/src/main/java/io/netty/buffer/UnsafeByteBufUtil.java`

`UnsafeByteBufUtil` 是所有基于 Unsafe 的 ByteBuf 操作的工具类，提供对原生地址和堆上数组的高效读写。

#### 2.3.1 核心设计：三层优化策略

每个读写方法都遵循相同的三层优化模式，以 `getInt` 为例：

```java
static int getInt(long address) {
    if (UNALIGNED) {
        int v = PlatformDependent.getInt(address);
        return BIG_ENDIAN_NATIVE_ORDER ? v : Integer.reverseBytes(v);
    }
    // 非对齐回退：逐字节拼装
    return PlatformDependent.getByte(address) << 24 |
           (PlatformDependent.getByte(address + 1) & 0xff) << 16 |
           (PlatformDependent.getByte(address + 2) & 0xff) <<  8 |
           PlatformDependent.getByte(address + 3)  & 0xff;
}
```

对于堆上数组版本，还有第四层 `VarHandle` 优化：

```java
static int getInt(byte[] array, int index) {
    if (UNALIGNED) {
        int v = PlatformDependent.getInt(array, index);
        return BIG_ENDIAN_NATIVE_ORDER ? v : Integer.reverseBytes(v);
    }
    if (USE_VAR_HANDLE) {
        return VarHandleByteBufferAccess.getIntBE(array, index);
    }
    // 逐字节拼装
    ...
}
```

**策略优先级**：
1. **Unsafe 非对齐访问**（最快）：单次内存访问 + 字节序转换
2. **VarHandle**（次快）：JVM 内部处理对齐和字节序
3. **逐字节拼装**（最慢）：多次 `getByte` 调用 + 位运算组合

#### 2.3.2 字节序处理

所有方法默认以 Big-Endian（网络字节序）读写。`getXxx` 方法读取后根据平台原生字节序决定是否需要翻转：

```java
// getShort（Big-Endian 输出）
short v = PlatformDependent.getShort(address);
return BIG_ENDIAN_NATIVE_ORDER ? v : Short.reverseBytes(v);

// getShortLE（Little-Endian 输出）
short v = PlatformDependent.getShort(address);
return BIG_ENDIAN_NATIVE_ORDER ? Short.reverseBytes(v) : v;
```

#### 2.3.3 setZero 的小块优化

```java
private static final int MAX_HAND_ROLLED_SET_ZERO_BYTES = 64;

static void setZero(long addr, int length) {
    if (length <= MAX_HAND_ROLLED_SET_ZERO_BYTES) {
        if (!UNALIGNED) {
            int bytesToGetAligned = zeroTillAligned(addr, length);
            addr += bytesToGetAligned;
            length -= bytesToGetAligned;
        }
        batchSetZero(addr, length); // 每次写 8 字节（long）
    } else {
        PlatformDependent.setMemory(addr, length, ZERO); // Unsafe.setMemory
    }
}
```

对于 64 字节以下的清零操作，手动展开为 `putLong` 调用比 `Unsafe.setMemory` 更快，因为后者需要处理线程状态切换的开销。对于非对齐地址，先逐字节对齐到 8 字节边界，再批量处理。

#### 2.3.4 内存拷贝的智能路由

```java
static void getBytes(AbstractByteBuf buf, long addr, int index, ByteBuf dst, int dstIndex, int length) {
    if (dst.hasMemoryAddress()) {
        // 目标是堆外内存：直接地址拷贝
        PlatformDependent.copyMemory(addr, dst.memoryAddress() + dstIndex, length);
    } else if (dst.hasArray()) {
        // 目标是堆上数组：地址到数组拷贝
        PlatformDependent.copyMemory(addr, dst.array(), dst.arrayOffset() + dstIndex, length);
    } else {
        // 复合 ByteBuf：委托给目标的 setBytes
        dst.setBytes(dstIndex, buf, index, length);
    }
}
```

根据目标 ByteBuf 的类型选择最高效的拷贝路径，避免不必要的中间缓冲区。

#### 2.3.5 Direct ByteBuf 的工厂方法

```java
static UnpooledDirectByteBuf newDirectByteBuf(ByteBufAllocator alloc, int initialCapacity, int maxCapacity) {
    if (PlatformDependent.hasUnsafe()) {
        if (PlatformDependent.useDirectBufferNoCleaner()) {
            return new UnpooledUnsafeNoCleanerDirectByteBuf(alloc, initialCapacity, maxCapacity);
        }
        return new UnpooledUnsafeDirectByteBuf(alloc, initialCapacity, maxCapacity, true);
    }
    return new UnpooledDirectByteBuf(alloc, initialCapacity, maxCapacity, true);
}
```

根据平台能力选择最优的 DirectByteBuf 实现：
- `UnpooledUnsafeNoCleanerDirectByteBuf`：使用 `Unsafe.allocateMemory`，无 Cleaner 开销
- `UnpooledUnsafeDirectByteBuf`：使用 Unsafe 操作但通过 Cleaner 释放
- `UnpooledDirectByteBuf`：纯 NIO 实现，无 Unsafe 依赖

### 2.4 ResourceLeakDetector — 资源泄漏检测器

**文件位置**：`common/src/main/java/io/netty/util/ResourceLeakDetector.java`

`ResourceLeakDetector` 是 Netty 资源泄漏检测的核心类，通过弱引用 + 引用队列机制，在对象被 GC 回收时检测是否正确调用了 `release()`。

#### 2.4.1 四种检测级别

```java
public enum Level {
    DISABLED,   // 禁用泄漏检测，零开销
    SIMPLE,     // 简单采样，仅报告是否有泄漏（默认）
    ADVANCED,   // 高级采样，报告泄漏对象的最近访问记录
    PARANOID    // 偏执模式，跟踪所有对象，仅用于测试
}
```

| 级别 | 采样策略 | 记录调用栈 | 性能开销 | 适用场景 |
|------|----------|-----------|----------|----------|
| DISABLED | 无 | 无 | 零 | 生产环境 |
| SIMPLE | 1/128 概率 | 仅创建栈 | 极低 | 生产环境默认 |
| ADVANCED | 1/128 概率 | 创建 + 最近访问栈 | 中等 | 预发布环境 |
| PARANOID | 100% | 创建 + 最近访问栈 | 高 | 开发/测试 |

通过系统属性配置：
- `-Dio.netty.leakDetection.level=advanced`（新）
- `-Dio.netty.leakDetectionLevel=4`（旧，兼容）
- `-Dio.netty.noResourceLeakDetection=true`（快捷禁用）

#### 2.4.2 采样率控制

```java
private static final int DEFAULT_SAMPLING_INTERVAL = 128;

private DefaultResourceLeak<T> track0(T obj, boolean force) {
    Level level = ResourceLeakDetector.level;
    if (force ||
            level == Level.PARANOID ||
            (level != Level.DISABLED && ThreadLocalRandom.current().nextInt(samplingInterval) == 0)) {
        reportLeak();
        return new DefaultResourceLeak<>(obj, refQueue, allLeaks, getInitialHint(resourceType));
    }
    return null;
}
```

- `SIMPLE` 和 `ADVANCED` 级别使用概率采样：`ThreadLocalRandom.current().nextInt(128) == 0`，即约 1/128 的对象会被跟踪
- `PARANOID` 级别跟踪所有对象（`force = true` 或级别判断）
- 采样间隔可通过 `-Dio.netty.leakDetection.samplingInterval` 配置，设为 2 的幂次可获得 TLR 性能优化

#### 2.4.3 DefaultResourceLeak — 弱引用追踪器

```java
private static final class DefaultResourceLeak<T>
        extends WeakReference<Object> implements ResourceLeakTracker<T>, ResourceLeak {
    private volatile TraceRecord head;        // 调用栈记录链表头
    private volatile int droppedRecords;      // 被丢弃的记录数
    private final Set<DefaultResourceLeak<?>> allLeaks;
    private final int trackedHash;            // 被跟踪对象的 identityHashCode
}
```

**核心设计**：
- 继承 `WeakReference`：不影响被跟踪对象的 GC
- 持有 `allLeaks` 集合引用：泄漏检测的核心数据结构
- `trackedHash`：存储被跟踪对象的 `identityHashCode`，用于 `close()` 时的断言校验，避免存储对被跟踪对象的强引用

#### 2.4.4 泄漏检测流程

```
资源创建时：                    资源释放时：                   GC 时：
  track(obj)                    tracker.close(obj)           WeakRef 入队 refQueue
    |                               |                            |
    v                               v                            v
  new DefaultResourceLeak       allLeaks.remove(this)        ref.dispose()
  (obj, refQueue, allLeaks)     clear()                      if !allLeaks.remove(this)
    |                           head = close mark               -> 已正常释放，跳过
    v                                                        else
  allLeaks.add(this)                                           -> 泄漏！生成报告
```

关键方法 `reportLeak()`：

```java
private void reportLeak() {
    for (;;) {
        DefaultResourceLeak<?> ref = (DefaultResourceLeak<?>) refQueue.poll();
        if (ref == null) break;
        if (!ref.dispose()) continue; // 已正常释放
        String records = ref.getReportAndClearRecords();
        if (reportedLeaks.add(records)) { // 去重：相同报告只输出一次
            if (records.isEmpty()) {
                reportUntracedLeak(resourceType);   // SIMPLE 级别
            } else {
                reportTracedLeak(resourceType, records); // ADVANCED/PARANOID 级别
            }
        }
    }
}
```

`reportedLeaks` 集合确保相同的泄漏报告只输出一次，避免日志洪水。

#### 2.4.5 调用栈记录的指数退避策略

`TraceRecord` 链表用于记录资源的访问历史。当记录数超过 `TARGET_RECORDS`（默认 4）时，使用指数退避策略丢弃旧记录：

```java
private void record0(Object hint) {
    if (TARGET_RECORDS > 0) {
        TraceRecord oldHead;
        TraceRecord prevHead;
        TraceRecord newHead;
        boolean dropped;
        do {
            if ((prevHead = oldHead = headUpdater.get(this)) == null ||
                    oldHead.pos == TraceRecord.CLOSE_MARK_POS) {
                return; // 已关闭
            }
            final int numElements = oldHead.pos + 1;
            if (numElements >= TARGET_RECORDS) {
                final int backOffFactor = Math.min(numElements - TARGET_RECORDS, 30);
                dropped = ThreadLocalRandom.current().nextInt(1 << backOffFactor) != 0;
                if (dropped) {
                    prevHead = oldHead.next; // 跳过旧记录
                }
            } else {
                dropped = false;
            }
            newHead = hint != null ? new TraceRecord(prevHead, hint) : new TraceRecord(prevHead);
        } while (!headUpdater.compareAndSet(this, oldHead, newHead));
        if (dropped) {
            droppedRecordsUpdater.incrementAndGet(this);
        }
    }
}
```

**退避机制**：
- 记录数 < `TARGET_RECORDS`：总是记录
- 记录数 >= `TARGET_RECORDS`：以 `1 / 2^n` 的概率丢弃最旧记录（`n` 为超出数量，最大 30）
- 使用 CAS 操作避免序列化，高竞争时可能放弃记录

**关键特性**：
- 当前记录总是被保留（CAS 失败时替换的是旧记录，不是新记录）
- 最后一次访问总是被记录
- 使用 `ThreadLocalRandom` 而非全局 Random，减少竞争

#### 2.4.6 TraceRecord — 调用栈记录

```java
private static class TraceRecord extends Throwable {
    private static final int BOTTOM_POS = -1;
    private static final int CLOSE_MARK_POS = -2;
    private static final TraceRecord BOTTOM = new TraceRecord(false) {
        @Override
        public Throwable fillInStackTrace() {
            return this; // 避免 ClassLoader 泄漏
        }
    };
    private final String hintString;
    private final TraceRecord next;
    private final int pos;
}
```

**设计精妙之处**：
- 继承 `Throwable`：利用 JVM 原生的 `fillInStackTrace()` 捕获调用栈，无需手动遍历
- `BOTTOM` 的 `fillInStackTrace()` 返回 `this`：避免填充栈帧导致 ClassLoader 泄漏（参见 PR #10691）
- `CLOSE_MARK_POS = -2`：标记已关闭的 tracker，防止关闭后继续记录
- `toString()` 中跳过前 3 帧（自身 + record0 + record），并过滤排除列表中的方法

#### 2.4.7 reachabilityFence 防止对象过早回收

```java
public boolean close(T trackedObject) {
    assert trackedHash == System.identityHashCode(trackedObject);
    try {
        return close();
    } finally {
        reachabilityFence0(trackedObject);
    }
}

private static void reachabilityFence0(Object ref) {
    if (ref != null) {
        synchronized (ref) { }
    }
}
```

**问题背景**：JVM 可能在方法执行过程中判定某个对象不再可达，从而在方法结束前触发其 `finalize()` 或 Cleaner。这会导致 `trackedObject` 在 `release()` 调用链中被提前回收。

**解决方案**：通过 `synchronized(ref)` 在方法返回前保持 `trackedObject` 的强可达性，等价于 JDK 9 的 `Reference.reachabilityFence()`。

#### 2.7.3 CleanerJava6 — JDK 8 的 Cleaner

**文件位置**：`common/src/main/java/io/netetty/util/internal/CleanerJava6.java`

```java
// 构造方法链：ByteBuffer -> DirectBuffer.cleaner() -> Cleaner.clean()
clean = lookup.findVirtual(cleanerClass, "clean", methodType(void.class));
clean = MethodHandles.guardWithTest(nullTest, clean, nullTest); // null 安全
clean = MethodHandles.filterArguments(clean, 0,
    lookup.findVirtual(directBufClass, "cleaner", methodType(cleanerClass)));
clean = MethodHandles.explicitCastArguments(clean, methodType(void.class, ByteBuffer.class));
```

**工作原理**：`DirectByteBuffer` 实现了 `DirectBuffer` 接口，其 `cleaner()` 方法返回关联的 `sun.misc.Cleaner` 对象。调用 `cleaner.clean()` 触发 `Unsafe.freeMemory` 释放原生内存。

#### 2.7.4 CleanerJava9 — JDK 9+ 的 Cleaner

**文件位置**：`common/src/main/java/io/netty/util/internal/CleanerJava9.java`

```java
MethodHandle invokeCleaner = lookup.findVirtual(
    unsafeClass, "invokeCleaner", methodType(void.class, ByteBuffer.class));
invokeCleaner = invokeCleaner.bindTo(PlatformDependent0.UNSAFE);
```

**与 JDK 8 的区别**：
- JDK 8 需要通过 `DirectBuffer.cleaner()` 获取 Cleaner 对象再调用 `clean()`
- JDK 9 直接通过 `Unsafe.invokeCleaner()` 一步完成，无需访问内部 API
- JDK 9 方法对 SecurityManager 做了特殊处理，避免权限检查开销

#### 2.7.5 CleanerJava24Linker — JDK 24+ 的 Linker 实现

**文件位置**：`common/src/main/java/io/netty/util/internal/CleanerJava24Linker.java`

针对 JDK 24+ 中 Unsafe 被限制的场景，通过 `java.lang.foreign.Linker` API 直接链接到 libc 的 `malloc()` 和 `free()`：

```java
// 通过 Linker API 创建 malloc 和 free 的 MethodHandle
MethodHandle mallocMethod = ...; // (long) -> long
MethodHandle freeMethod = ...;   // (long) -> void
MethodHandle wrapMethod = ...;   // (long, long) -> ByteBuffer
```

**工作原理**：
1. 通过 `Linker.nativeLinker().defaultLookup().find("malloc")` 获取 malloc 符号
2. 通过 `Linker.nativeLinker().downcallHandle()` 创建调用句柄
3. 分配：`malloc(capacity)` -> `MemorySegment.ofAddress(addr).asByteBuffer()`
4. 释放：`free(memoryAddress)`

**前提条件**：需要在 `io.netty.common` 模块中启用 native access 权限，且仅支持 64 位平台。

#### 2.7.6 CleanerJava25 — JDK 25+ 的 Arena 实现

**文件位置**：`common/src/main/java/io/netty/util/internal/CleanerJava25.java`

使用 JDK 25+ 的 `Arena.ofShared()` API：

```java
// 等价代码：
Arena arena = Arena.ofShared();
MemorySegment segment = arena.allocate(size);
ByteBuffer buffer = segment.asByteBuffer();
long address = segment.address();
// 释放时：arena.close();
```

通过复杂的 MethodHandle 链组合实现了上述逻辑。**注意**：`hasExpensiveClean()` 返回 `true`，因为关闭共享 Arena 需要跨线程握手，开销较大。

#### 2.7.7 DirectCleaner — 最优路径

**文件位置**：`common/src/main/java/io/netty/util/internal/DirectCleaner.java`

当 Unsafe 可用且支持无 Cleaner 构造 DirectByteBuffer 时使用：

```java
public CleanableDirectBuffer allocate(int capacity) {
    return new CleanableDirectBufferImpl(capacity); // -> Unsafe.allocateMemory
}

public CleanableDirectBuffer reallocate(CleanableDirectBuffer old, int newCapacity) {
    ByteBuffer newBuffer = PlatformDependent0.reallocateDirectNoCleaner(old.buffer(), newCapacity);
    return new CleanableDirectBufferImpl(newBuffer);
}
```

`DirectCleaner` 直接操作原生内存，不经过 JDK 的 DirectByteBuffer 分配/释放流程，性能最优。同时支持 `reallocate` 原地扩容，避免重新分配。

#### 2.7.8 NOOP Cleaner — 降级兜底

`PlatformDependent` 中定义的匿名 NOOP 实现：

```java
private static final Cleaner NOOP = new Cleaner() {
    @Override
    public CleanableDirectBuffer allocate(int capacity) {
        return new CleanableDirectBuffer() {
            private final ByteBuffer byteBuffer = ByteBuffer.allocateDirect(capacity);
            @Override public ByteBuffer buffer() { return byteBuffer; }
            @Override public void clean() { /* NOOP — 依赖 GC 回收 */ }
        };
    }
};
```

当没有可用的 Cleaner 时，分配标准 JDK `DirectByteBuffer`，`clean()` 为空操作，依赖 GC 的 Finalizer 机制回收。

## 三、设计思想

### 3.1 渐进式降级策略

Netty 的堆外内存管理采用严格的降级链：

```
DirectCleaner (Unsafe.allocateMemory)
    ↓ 不可用
CleanerJava9 (Unsafe.invokeCleaner)
    ↓ 不可用
CleanerJava24Linker (Linker -> malloc/free)
    ↓ 不可用
CleanerJava25 (Arena.ofShared)
    ↓ 不可用
NOOP (ByteBuffer.allocateDirect + GC)
```

每一层都有 `isSupported()` 检查，确保在任何平台上都能找到可用的内存管理方案。

### 3.2 采样检测权衡

泄漏检测的采样率设计体现了**性能与可检测性的权衡**：
- `SIMPLE`：1/128 采样 + 无调用栈记录，几乎零开销
- `ADVANCED`：1/128 采样 + 指数退避调用栈记录，适度开销
- `PARANOID`：100% 跟踪 + 完整记录，仅用于开发/测试

指数退避策略确保即使在高频访问场景下，记录数量也不会无限增长，同时保证最后一次访问和创建记录始终被保留。

### 3.3 WeakReference + ReferenceQueue 模式

这是 Java 中经典的泄漏检测模式：
1. 创建资源时，将其包装为 `WeakReference` 并注册到 `ReferenceQueue`
2. 资源正常释放时，从 `allLeaks` 集合移除
3. GC 回收时，如果 `WeakReference` 仍在 `allLeaks` 中（未被 `close()` 移除），则说明泄漏
4. `ReferenceQueue.poll()` 获取待处理的引用，检查是否泄漏

### 3.4 MethodHandle 替代反射

Netty 4.2 大量使用 `MethodHandle` 替代传统反射：
- 启动时一次性解析并缓存 MethodHandle
- 运行时调用 MethodHandle 的开销接近直接方法调用
- 支持 `invokeExact` 避免装箱/拆箱
- 通过 `MethodHandles.filterArguments`、`foldArguments` 等组合子构建复杂调用链

## 六、学习要点

### 6.1 Unsafe 操作的三个关键认知

1. **Unsafe 不是"不安全"**：它是指绕过 JVM 安全检查直接操作内存，需要开发者自行保证安全性。Netty 通过封装层将 Unsafe 的使用限制在可控范围内。

2. **非对齐访问的平台差异**：x86/x64 天然支持非对齐内存访问（只是略慢），但 ARM/SPARC 可能因非对齐访问触发硬件异常。Netty 的 `UNALIGNED` 检测确保在所有平台上安全运行。

3. **SafePoint 轮询的必要性**：JDK 8 的 `Unsafe.copyMemory` 可能长时间不返回，阻止 JVM 在 SafePoint 进行 GC。Netty 将大块拷贝拆分为 1MB 小块来解决此问题。

### 6.2 泄漏检测的工程智慧

1. **弱引用不影响 GC**：使用 `WeakReference` 跟踪对象，不会阻止对象被 GC 回收，避免检测机制本身造成内存问题。

2. **采样而非全量**：默认 1/128 的采样率将开销降到极低，适合生产环境。`PARANOID` 模式用于开发/测试阶段的全面检测。

3. **指数退避记录**：在高频访问场景下，通过概率丢弃旧记录来控制内存开销，同时保证关键记录（创建栈和最后一次访问）不丢失。

4. **`reachabilityFence` 防止 JVM 过早回收**：JVM 可能在方法执行过程中判定对象不可达。通过 `synchronized(ref)` 保持强可达性。

### 6.3 Cleaner 演进的启示

Netty 的 Cleaner 演进史反映了 Java 平台的发展：
- JDK 8：`sun.misc.Cleaner` + `DirectBuffer.cleaner()`（内部 API）
- JDK 9：`Unsafe.invokeCleaner()`（标准 Unsafe 方法）
- JDK 24+：`Linker` API 直接调用 libc（绕过 Unsafe 限制）
- JDK 25+：`Arena.ofShared()`（标准 MemorySegment API）

每一步演进都保持了向后兼容和渐进式降级，这是一个大型开源项目在 JVM 版本迭代中维护兼容性的典范。
